# Aheadscale: GitHub Actions и изолированный тестовый стенд

Дата: 29 октября 2026 года. Статус: схема подготовлена к согласованию.
Владелец выбрал гибрид GitHub runners + изолированный стенд. Работает один агент.

## Цель и границы

Агент выбирает необходимые проверки, запускает GitHub Actions и получает
краткий машинный результат. Установка клиентов, перезагрузки, опрос состояний,
передача данных и очистка выполняются обычными программами, без участия модели
в каждом шаге. Полные логи нужны агенту только для разбора конкретного FAIL.

Перенос охватывает существующие проверки Aheadscale и постепенно автоматизирует
сценарии единого плана. Это не обещание мгновенно получить автоматизированные
100% GUI-тестов. В четырёх планах сейчас 100 уникальных идентификаторов сценариев,
включая RG01–RG47; каждый получает явный статус переноса. Новые фичи сервера,
публичные релизы и отложенный поиск задержек подключения в этот этап не входят.
RG39 сохраняет согласованную семантику, а не исправляется в рамках переноса.

## Что уже есть

- Публичный `pomozoff/aheadscale-client`, основная удалённая ветка `aheadscale`.
- `aheadscale-client.yml`: часть Go/Python регрессий, платформенные сборки,
  проверки установки Linux и SHA256 артефактов. Запуск тестов сейчас связан
  со сборкой слишком широкого набора платформ.
- `aheadscale-windows-vpn-prototype.yml`: native-компонент и Windows установщики.
- Локальный адаптированный NM-плагин: собственные Go/D-Bus и CTest проверки;
  его исходники должны восстанавливаться из закреплённого patch/source manifest.
- Реальные сценарии на ВМ сейчас выполнялись через SSH/QMP/AT-SPI и отдельные
  команды. Их нужно превратить в версионируемые сценарии, а не запускать агентом.
- Собственных GitHub runners нет. На Mac mini около 23 ГБ свободного диска
  и 10 ГБ доступной RAM; на MacBook одновременно работают максимум две ВМ.

## Выбранная архитектура

### 1. GitHub-hosted: быстрые тесты и сборки

Публичный клиентский репозиторий содержит тесты без доступа к личной сети:
Go/Python/CTest регрессии, проверки контрактов, сборку и аудит установщиков.
Отдельные наборы: `unit`, `packaging`, `networkmanager`, `windows-native`,
`build`, `release-check`. Наборы не заставляют пересобирать GUI ради проверки
упаковки или документации. Сборка создаёт неизменяемый комплект с source SHA,
версиями инструментов, платформой, ревизией пакета и SHA256 каждого файла.
Desktop и CLI для перехода всегда берутся из согласованной ревизии.

Сборки выполняются на соответствующей архитектуре там, где это требуется.
macOS Intel не добавляется обратно в текущую сборочную матрицу без отдельного
решения владельца. Ubuntu/Fedora, Windows x64/ARM64 и macOS ARM64 сохраняются
в каталоге целевых проверок; отсутствие исполнителя не превращается в PASS.

### 2. Закрытый `pomozoff/aheadscale-tests`: проверки реальных ОС

Этот отдельный приватный репозиторий запускает `desktop`, `cli`, `lifecycle`,
`network`, `regression` и итоговый `acceptance`. Его собственный runner работает
в отдельной одноразовой управляющей ВМ. Публичный форк не получает runner,
ключей личной сети или доступа к Mac mini. Код внешнего pull request никогда
не исполняется на закрытом стенде автоматически.

Управляющая ВМ не перезагружается вместе с проверяемой ОС. Она хранит журнал
шагов вне гостя, пережидает reboot, проверяет новый boot ID, запуск GUI/службы,
статус системного VPN, реальные IP/DNS/HTTP и очистку. После Connecting → Cancel
проверяются отсутствие туннеля и позднего Up, а не только текст GUI.
Драйверы GUI используют имеющиеся штатные интерфейсы: Linux AT-SPI,
Windows UI Automation, macOS Accessibility. Для каждого DE отдельные проверки
системной панели; вызов nmcli/CLI не засчитывается вместо нажатия кнопки UI.

### 3. Изоляция и состояние ВМ

Проверки установки/удаления выполняются на выделенных клонах эталонных образов.
Существующие пользовательские ВМ не откатываются и не удаляются. Снимки/образы
создаются только после проверки места, корректного выключения и происхождения.
Перед первым destructive-сценарием должны быть проверены восстановление образа
и доступ к независимому каналу управления. Сброс стенда после прогона обязателен.

Runner не получает Docker socket хоста, домашний каталог, GPG-ключ владельца,
root SSH к Mac mini или произвольную командную строку управляющего сервиса.
Операции гипервизора ограничены заранее зарегистрированными ID тестовых ВМ:
создать overlay, запустить, остановить, восстановить; блокировка исключает
одновременное использование одной ВМ. Привилегии для VPN/установщиков находятся
внутри выделенных гостей. Личный Tailscale и рабочий сервер Aheadscale не
используются как тестовые зависимости. Защитные проверки TLS/Polkit/SELinux
и правила владения ресурсами сохраняются.

Сначала автоматизируется x64 Linux на Mac mini. Подключение провайдера MacBook
для ARM64/macOS — отдельный шаг готовности доступа; недоступный MacBook даёт
BLOCKED/NOT_RUN, не бесконечные повторные обращения к агенту. Одновременно
не больше одного тяжёлого сценария на Mac mini; на MacBook — не больше двух
гостей с учётом второго сетевого узла. Любой запуск имеет лимит времени и места.
Переезд вычислений в облако не производится автоматически и не меняет бюджет.

### 4. Тестовая серверная часть и вход

Для сетевых и auth-проверок нужен изолированный тестовый сервер Aheadscale,
синтетические аккаунты и отдельный тестовый провайдер входа. Существующий
upstream E2E-harness переиспользуется там, где совместим; он не считается
автоматической заменой проверки Aheadscale-регистрации и собственного UI входа.
Письма попадают в тестовый почтовый приёмник. Ключи ограничены тестовым аккаунтом,
живут один прогон и не появляются в логах/артефактах. Аккаунт владельца, его
пять устройств и `aheadscale.ru` не используются для регулярных CI-прогонов.
Новые shared/production PostgreSQL, MinIO и прочие сервисы не создаются.

Настоящий вход через VK/Яндекс с MFA/согласием, пользовательские TCC-разрешения
macOS и оценка качества визуального оформления могут требовать человека.
Такие пункты явно помечаются MANUAL. Системные разрешения подготавливаются
один раз штатно; отключение защит ОС не является способом автоматизации.
Непокрытые проверки не заменяются успешным входом по setup key.

## Единый контракт запуска и результата

Ручной запуск Actions выбирает `suite`, `platform`, `architecture`, `cases`,
`candidate_run_id` и при необходимости `previous_run_id`. Значения — проверяемые
перечисления/идентификаторы; произвольных shell-команд в inputs нет.
Артефакт загружается из конкретного завершённого workflow и сверяется по SHA.
В сводке всегда видны source SHA и SHA установщика; старый зелёный запуск
не может подтвердить новый пакет.

Каталог сценариев связывает существующий ID с исполнителем, платформами,
предусловиями и командой. Статусы: PASS, FAIL, BLOCKED, NOT_RUN, MANUAL, N/A.
N/A разрешён только по явно заданной применимости. Неизвестный ID — ошибка.
Две разновидности итогов различаются: «выбранный набор PASS» и «релиз принят».
Итоговая приёмка требует всех обязательных сценариев для заявленной матрицы.
Ошибка очистки делает запуск неуспешным; недоступный стенд не даёт зелёную
приёмку. Ошибка продукта не маскируется автоматическим повтором до успеха.

Каждый запуск сохраняет краткий `GITHUB_STEP_SUMMARY`, `results.json` и JUnit.
Важные поля: scenario ID, ОС/архитектура/DE, результат, причина, source/artifact
SHA и ссылка на диагностические файлы. Полные логи и снимки синтетического UI
хранятся отдельно с коротким сроком хранения; секреты редактируются до загрузки.
Очистка выполняется также при FAIL/Cancel/timeout, а watchdog убирает ресурсы
с подтверждённым ID прогона после аварии. Никакого общего prune.

Агент делает один dispatch выбранного набора. Ожидание выполняется обычным
процессом/API, без анализа промежуточного вывода моделью и частого опроса.
После завершения агент читает одну сводку; при FAIL получает только журнал
нужного сценария. Повторная сборка и полный прогон не запускаются по умолчанию.

## Порядок реализации и критерии приёмки

1. Развязать существующие быстрые проверки и сборки, перенести реально
   выполнявшиеся команды в scripts, сделать отчёт и запуск выбранного набора.
   Первый настоящий Actions-прогон должен пройти на точном source SHA.
2. Завести каталог всех 100 ID, сопоставить существующие регрессии и показать
   оставшиеся MANUAL/NOT_RUN. Перенести fixture плагина/D-Bus/CTest и закрепить
   среду сборки KDE; неизвестные или пропущенные обязательные тесты — не PASS.
3. Подготовить приватный репозиторий, изолированный worker и Linux x64 lab.
   Доказать reset/cleanup и ограничения доступа, затем выполнить установку,
   ON/OFF/Cancel/restart, Desktop↔CLI, reinstall/reboot, двусторонний IP/DNS/HTTP.
4. Подключить ARM64 Linux, Windows и macOS исполнители, перенести их накопленные
   регрессии. Для каждого сценария сравнить Actions-результат с прежним ручным
   свидетельством. Завершить картой покрытия и командой запуска для агента.

Нельзя объявить «всё перенесено», пока вместо любого ранее выполнявшегося
прогона агент всё ещё вручную копирует команды по SSH, за исключением явно
перечисленных человеческих шагов. Внедрение не закрывает неисполненные тесты
и не заменяет публичную подпись установщиков.
