# План реализации прототипа Windows VPN Aheadscale

> **Для исполнителя:** применять `superpowers:executing-plans`, выполнять задачи последовательно и отмечать шаги. Пользователь выбрал одного агента; подагенты и отдельные проверяющие не запускаются.

**Цель:** проверить на Windows 11 ARM64 полноценный профиль Aheadscale с управлением из системных настроек и настоящим обменом с Ubuntu.

**Архитектура:** отдельный пакет MSIX содержит C++/WinRT VPN-плагин и процесс-посредник с полным доверием Windows desktop. Go-служба сохраняет аккаунт и движок WireGuard, а опытный адаптер получает и возвращает IP-пакеты через защищённую локальную связь. Доступность этой связи проверяется до вмешательства в действующий backend.

**Технологии:** Go 1.26.7; C++/WinRT и Windows SDK 10.0.26100.0; MSBuild/v143; Windows VPN API; MSIX; существующие go-winio, WireGuard-Go и IPC-аутентификация. Новые зависимости Go не требуются.

**Спецификация:** [проект первого этапа](../specs/2026-10-19-windows-vpn-integration-design.md), согласован пользователем 2026-10-19. [Исследование](../../aheadscale/windows-vpn-research.md).

## Общие ограничения

- Работа одним агентом, последовательно, в существующем изолированном worktree `codex/aheadscale-client`; прежние staged/unstaged изменения сохраняются.
- Операторская VM — Windows 11 ARM64; Ubuntu используется как второе устройство. Windows AMD64, Linux и macOS не пересобираются.
- Производственный сервер и существующая авторизация не изменяются. Ключи устройства и токены не экспортируются из службы.
- Отдельные имя пакета `Aheadscale.VpnPrototype`, Publisher `CN=Aheadscale VPN Prototype`, профиль `Aheadscale Prototype` отделяют опытную установку от рабочего клиента `.8`.
- Windows VPN API владеет интерфейсом, адресом и маршрутами опытного канала. Для активного опытного режима второй Wintun-интерфейс с теми же маршрутами не создаётся.
- Сертификат разработки создаётся в изолированном Windows-процессе сборки; закрытый ключ не входит в артефакты. На VM устанавливается только публичный сертификат в TrustedPeople. Изменений Trusted Root, обхода проверки подписи и обновления ОС нет.
- До установки зафиксировать SHA256 пакета, отпечаток сертификата, владельца установки и команды удаления. Сохранить работоспособный установщик `.8` для отката.
- Видимость профиля и сообщение Connected отдельно не считаются успешным сетевым тестом.
- Документы и отчёты — по-русски. Автоматическая публикация пользователям и изменения CDN в этот план не входят.

## Особое внимание при проверке

1. Служба остановлена или устройство ещё не зарегистрировано: подключение не должно оставаться Connected.
2. Отключение из Windows во время восстановления: приложение не включает канал снова вопреки действию пользователя.
3. Подключился другой локальный пользователь или пакет: управление, данные и приватные ключи недоступны.
4. Обрыв IPC, обрезанный кадр, чрезмерный размер: канал закрывается без зависания, чтения чужой памяти и неограниченного выделения.
5. Повторная установка и откат: удаляются только опытные профиль, пакет и сертификат; регистрация `.8` сохраняется.

## Задача 1. Собираемый пакет, настоящий профиль и проверка границы процессов

**Файлы:**
- Создать `packaging/windows-vpn-prototype/CMakeLists.txt` и `src/background_task.cpp`: активация `IBackgroundTask` и обработка VPN-событий.
- Создать `src/vpn_plugin.cpp`, `src/vpn_plugin.h`: реализация `IVpnPlugIn`.
- Создать `src/profile_controller.cpp`: команды `add`, `status`, `connect`, `disconnect`, `remove` для принадлежащего пакету профиля.
- Создать `Package.appxmanifest`, `scripts/build.ps1`, `scripts/install-test.ps1`, `scripts/remove-test.ps1`.
- Создать `.github/workflows/aheadscale-windows-vpn-prototype.yml`: ручная Windows-сборка ARM64 и сохранение опытных артефактов.

**Интерфейсы:** C++ `winrt::hstring ProfileName()` возвращает `Aheadscale Prototype`; `IVpnPlugIn::Connect/Disconnect` вызываются платформой. Контроллер возвращает JSON с `profileName`, `packageFamilyName`, `connectionStatus` и код завершения. Параметров с ключами или паролями нет.

- [ ] Зафиксировать исходное состояние VM: версия `.8`, идентичность устройства, отсутствие опытного пакета/профиля/сертификата.
- [ ] Подготовить SDK/MSBuild в Windows-среде сборки. Проверить точную версию SDK; отсутствие инструмента — ошибка подготовки, а не пропуск проверки. Приложение не устанавливать на runner.
- [ ] Собрать минимальный ARM64-плагин и контроллер. В Connect до готовности движка завершать попытку с понятной ошибкой; не выставлять фиктивное Connected.
- [ ] Создать профиль через `VpnManagementAgent` и `VpnPlugInProfile`, связать его с собственной Package Family Name; проверить видимость и реальный вызов Connect/Disconnect на VM.
- [ ] В обработчике Connect получить контекст процесса: AppContainer, пользователь, Package Family Name и доступный путь связи с посредником. Проверить доверенную связь внутри пакета и затем существующий защищённый IPC службы от desktop-посредника.
- [ ] Проверить отказ при остановленной службе и обращении из неподходящего локального контекста. Разрешения существующего IPC не расширять.
- [ ] Если поддерживаемая аутентифицированная связь не установлена, остановиться с точным HRESULT/Win32-кодом, контекстом и отчётом. Задачи 2–4 до доказательства этой границы не начинать; изменение архитектуры согласовать отдельно.

**Проверка:** `build.ps1 -Architecture arm64 -SdkVersion 10.0.26100.0` завершён с кодом 0; MSIX валиден и подписан, закрытый ключ отсутствует в артефакте. На VM контроллер `add/status/connect/disconnect/remove` подтверждает фактические результаты. При остановленной службе Connect завершается ошибкой, Windows не показывает Connected.

## Задача 2. Ограниченный канал пакетов и устройство WireGuard

**Файлы:**
- Создать `client/internal/windowsvpn/frame.go`, `frame_test.go`: двунаправленное кадрирование и ограничения размера.
- Создать `client/internal/windowsvpn/conn_tun.go`, `conn_tun_test.go`: реализация `tun.Device` поверх уже авторизованного соединения.
- Создать `packaging/windows-vpn-prototype/src/packet_bridge.cpp`, `packet_bridge.h`: передача буферов платформы и завершение сессии.
- Создать `src/desktop_broker.cpp`: подтверждённый в задаче 1 переход от пакетного процесса к службе; не принимает публичные TCP-соединения.

**Интерфейсы:** Go `ReadFrame(io.Reader, []byte) (int, error)`, `WriteFrame(io.Writer, []byte) error`, `NewConnTun(net.Conn, string, int) (tun.Device, error)`. Канал открывается только после проверки пользователя и пакета. Кадр: длина payload как uint32 little endian, затем полный IP-пакет; максимум 65535 байт. MTU опытного устройства — 1280.

- [ ] Написать узкие тесты на настоящий поток: точное сохранение IPv4-пакета в обе стороны, частичные чтения, короткий заголовок, оборванный payload, длины 0 и 65536. Ошибочные кадры завершают сеанс.
- [ ] Выполнить `go test ./client/internal/windowsvpn -count=1` и подтвердить отказ до реализации кодека.
- [ ] Реализовать ограниченный кодек и `tun.Device`; не журналировать пакеты. Close идемпотентен и разблокирует ожидающие Read/Write.
- [ ] Добавить проверки закрытия при заблокированном чтении и повторного Close; выполнить `go test -race ./client/internal/windowsvpn -count=1`.
- [ ] Соединить настоящий процесс плагина и desktop-посредника по подтверждённому пути. Передать известный IPv4-пакет в обоих направлениях, проверить длину и байты на другой стороне. Отказ другого пользователя/пакета закрепить реальной проверкой на VM.

**Проверка:** оба Go-прогона имеют код 0; межпроцессный обмен на VM сохраняет байты и закрывается при разрыве. Локальный echo без подтверждённой границы процессов недостаточен.

## Задача 3. Подключение к текущему движку и владение маршрутизацией

**Файлы:**
- В `client/iface/iface_new.go` ограничить существующую фабрику условием `(!windows || !windowsvpnprototype)` в дополнение к прежним build tags; тело обычной фабрики сохранить.
- Создать `client/iface/iface_new_vpn_windows.go` с `//go:build windows && windowsvpnprototype` и той же функцией `NewWGIFace(opts WGIFaceOpts) (*WGIface, error)`, создающей опытное устройство. Netstack-ветку сохранить.
- Создать `client/iface/device/device_windows_vpn.go`: `VpnTunDevice`, использующий ConnTun и существующие `ICEBind`, WireGuard-Go и WGConfigurer.
- Изменить только необходимые Windows-ветки `client/internal/engine.go`, маршрутизации и DNS: режим Windows VPN получает системный интерфейс из платформы.
- Создать `packaging/windows-vpn-prototype/src/channel_config.cpp`: адреса, маршруты и приватный DNS для VpnChannel.

**Интерфейсы:** `VpnTunDevice` выполняет существующий контракт `iface.WGTunDevice`. Обычный backend остаётся выбранным в стандартном клиенте; опытный выбирается только в специально собранном варианте `windowsvpnprototype`. `SessionConfiguration` содержит `Address netip.Prefix`, `MTU uint16`, `Routes []netip.Prefix`, `DNSDomains []string`, `DNSServers []netip.Addr`; ключей и токенов нет.

- [ ] Перед изменением фабрики проверить фактические вызовы WGTunDevice и записи маршрутов/DNS. Сопоставить каждую запись с единственным владельцем.
- [ ] Добавить проверку, что обычная Windows-сборка создаёт прежнее устройство, а опытная — ConnTun. Проверить отсутствие второго адаптера с теми же адресами.
- [ ] Реализовать VpnTunDevice и включение только в опытной сборке. Существующие профили аккаунта не преобразовывать.
- [ ] Передать VpnChannel реальную конфигурацию из службы. Освобождать канал при любом сбое до завершения Connect.
- [ ] Выполнить применимые существующие тесты затронутых пакетов, скомпилировать обычный и опытный Windows ARM64 CLI. Сетевые проверки выполнять только на VM.
- [ ] Проверить HTTP из Windows к Ubuntu по VPN IP; сопоставить фактический интерфейс/маршрут с каналом Windows VPN. Обмен через оставшийся старый Wintun не засчитывается.

**Проверка:** в опытном режиме настоящий HTTP проходит через системный VPN-канал; обычная сборка сохраняет прежнее поведение. При неработающем пути пакетов Connected не считается готовностью этапа.

## Задача 4. Управление из двух UI и браузерный вход

**Файлы:**
- Создать `packaging/windows-vpn-prototype/src/session_controller.cpp`, `session_controller.h`: согласование команд и состояний.
- Создать платформенный адаптер `client/ui/services/windows_vpn_controller_windows.go`; в опытном режиме адаптировать `Connection.Up`, `Connection.Down` и `Connection.WaitSSOLoginAndUp` в `client/ui/services/connection.go`, сохранив обычный путь остальных платформ.
- Добавить собственные опытные команды посредника `connect`, `disconnect`, `status`, `activate-login`, без смены существующего публичного RPC.

**Интерфейсы:** типизированные состояния `Disconnected`, `Connecting`, `Connected`, `Reconnecting`, `Failed`; сессия имеет идентификатор поколения. Ответы от старого поколения игнорируются. Управление Windows VPN выполняется пакетным контроллером, обычный GUI вне опытного режима работает как прежде.

- [ ] Зафиксировать тестами действие Disconnect во время Connect/Reconnecting и поздний ответ предыдущей сессии; конечное состояние остаётся Disconnected.
- [ ] Связать кнопки приложения с управлением профилем Windows. Непосредственные действия пользователя из Windows отражаются в приложении без обратного цикла автоподключения.
- [ ] Для NeedsLogin открыть существующий браузерный вход в пользовательском сеансе; сохранить обработчик callback до завершения. Плагин получает только итог готовности, а не токены.
- [ ] Проверить подключение из Windows после сохранённой регистрации; отдельно пройти браузерный вход с ручным вводом владельцем VM, если он требуется. Автоматический ввод пароля и создание чужого тестового аккаунта исключены.
- [ ] Остановить опытную службу: проверить переход системного профиля из Connected и понятную ошибку. Затем проверить восстановление без новой регистрации.

**Проверка:** реальные переключатели Windows и Aheadscale показывают согласованные состояния; намеренное отключение сохраняется; остановка службы не оставляет профиль подключённым.

- Создать `docs/aheadscale/smoke-results/2026-10-19-windows-vpn-prototype.md`: фактический отчёт, версии и SHA256; NOT_RUN/BLOCKED не превращать в PASS.
- Дополнить `docs/aheadscale/preview-report.md` ссылкой на результат и границами поддержки.

- [ ] Сверить текущие пакет, профиль и сертификат с сохранённым манифестом; удаление чужих объектов завершать отказом.
- [ ] Выполнить шесть HTTP-проверок с разными маркерами: по VPN IP, полному и короткому имени в обе стороны. Для каждого нужны HTTP 200, правильный маркер и реальный VPN IP удалённого устройства.
- [ ] Повторить обмен после Disconnect/Connect из Windows и из приложения, а также после перезапуска службы. Проверить сохранение идентичности и обычного интернета/DNS.
- [ ] Выполнить настоящую перезагрузку VM через сохранённый SSH-доступ. Перезапуск службы не выдавать за перезагрузку ОС.
- [ ] Проверить удаление опытной установки и повторную установку. После отката восстановить `.8`, сверить регистрацию и связь с Ubuntu.
- [ ] Удалить временные HTTP-сервисы и их правила firewall. Удалить только опытный сертификат доверия по сохранённому отпечатку; не передавать закрытый ключ в отчёт или артефакты.
- [ ] Сохранить отчёт и воспроизводимые артефакты. Публикацию обычным пользователям не выполнять.

**Проверка:** итоговый отчёт ссылается на наблюдаемые результаты каждого критерия спецификации. Неизвестные ограничения, включая AppContainer/IPC, DNS и перезагрузку, названы явно.

## Проверка плана перед исполнением

- Все критерии спецификации распределены: системный профиль — задача 1; реальный канал — задачи 2–3; вход/согласование/сбой — задача 4; сеть, перезапуск и откат — задача 5.
- Ограничения локальной связи требуют реального эксперимента в задаче 1. Неподтверждённый транспорт не принимается как факт и не обходится расширением прав.
- Точный способ связи внутри пакета выбирается по результату эксперимента; изменение границ архитектуры требует нового согласования, а не скрытого обходного решения.
- Перед реализацией пользователь просматривает этот план. Способ исполнения уже выбран: один агент в текущей сессии.
