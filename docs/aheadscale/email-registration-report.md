# Регистрация с подтверждением email: результаты 29–30 октября 2026 года

## Реализовано в кандидате

Порядок: email → одноразовая ссылка → пароль → штатный вход клиента.
До доказательства владения адресом активная личность и сеть не создаются.
Заявки, ограничения отправки и зарезервированный ID сохраняются в БД;
перезапуск не обнуляет их. Одновременное завершение и повтор после частичного
сбоя защищены отдельным захватом заявки и идемпотентным созданием личности.

Пароль не отправляется по почте и не хранится в заявке. В БД лежит хеш токена,
в письме — ссылка с фрагментом. GET не активирует аккаунт; повторная отправка
отменяет старую ссылку. Исходная попытка OAuth продолжается только в исходном
браузере. Другой браузер может завершить регистрацию, но не выдать инициатору
сессию. Существующие аккаунты и пароли сохраняются.

SMTP поддерживает обязательный STARTTLS или TLS с начала соединения, проверку
сертификата и секрет из закрытого файла. Без настроенной почты регистрация
закрыта, обычный вход работает. Параметры и DNS: [инструкция](email-delivery.md).

Семь браузерных групп:

1. Валидация email, маскирование пароля, явная кнопка показа и брендинг.
2. Регистрация по письму, новый вход, изоляция A/B и повторный email без смены пароля.
3. State, неправильный PKCE verifier и отказ повторному authorization code.
4. Реальная gRPC-регистрация пяти устройств, отказ шестому, запрет чужого
   удаления, удаление своего и освобождение слота. Квота задана в тестовой БД.
5. Чужой Origin, неверная/использованная ссылка и GET без активации.
6. Регистрация в другом браузере без автоматического входа инициатора.
7. Повторное письмо, отказ старой ссылке и сохранение исходной попытки OAuth.

Тестовые письма и данные синтетические. Контейнер не отправляет почту наружу;
SMTP-приёмник принимает её по настоящему TLS. Ключи и БД одноразовые, удаляются
после проверки. Артефакты содержат JSON, JUnit и очищенную диагностику;
нет паролей, OAuth-кодов, скриншотов или browser trace.

## Исправленные несовместимости и незакрытые наблюдения

- Политика form-action страницы подтверждения блокировала переход Chromium к
  localhost после успешного входа Dex. Разрешены только адреса двух уже
  зарегистрированных OAuth-клиентов, без wildcard. Проверены защита от
  вставки CSP и отсутствие POST с паролем на локальном callback.
- Относительные штатные device callback Dex ошибочно закрывали регистрацию
  при проверке списка адресов. Их origin уже покрывается self; они исключены
  из списка дополнительных источников. Оба варианта добавлены в регрессию.
- В прогоне `40862419659` последний inspect оставил форму скрытой. Следующий
  прогон с явной проверкой HTTP-статуса прошёл. После переноса кандидата в main-ветку такой же сценарий снова не прошёл
  (`40864780990`). Набор делает около 31 защищённого запроса за 10 секунд,
  тогда как общий HTTP-лимит даёт 20 запросов сразу и по одному в секунду.
  Тестовый трафик согласован с этим бюджетом без изменения сервера; добавлена
  явная проверка HTTP-ответа завершения. Конкретный статус первоначальных
  отказов журнал не сохранил, поэтому связь с лимитом остаётся гипотезой.
- При переносе кандидата в main запуск `40864205163` не начал браузерные
  сценарии: отсутствовал общий модуль отчётов testing/aheadscale/run.py.
  Модуль перенесён отдельно, каталог прошёл. Это не результат проверки продукта.

## Реальная регистрация 30 октября 2026 года

- Новый адрес Яндекс Почты до отправки отсутствовал в локальном хранилище
  учётных записей. Рабочий сервер принял запрос регистрации с HTTP 202.
- Владелец подтвердил: фирменное письмо пришло во «Входящие», оформление
  корректное, переход по кнопке и задание пароля завершились созданием аккаунта.
- После этого операторская проверка БД подтвердила `state=done` и заполненный
  `verified_at`. **PASS** для доставки в Яндекс, визуальной ручной проверки
  письма и завершения новой регистрации. Пароль и одноразовая ссылка не
  запрашивались в чате и не сохранялись в отчёте.
- Предыдущая попытка с адресом Mail.ru оказалась повторной регистрацией уже
  существующего аккаунта. Его ID отличался от зарезервированного ID заявки;
  при этом ссылка имела правильный формат, совпадала с хешем заявки, не истекла
  и принималась `/oauth2/signup/inspect` с HTTP 200. Завершение регистрации
  безопасно отклонялось, прежний пароль не изменялся.
- **Дефект сообщения исправлен следующим кандидатом:** ранее ошибка
  существующего аккаунта превращалась в `ErrToken` и показывала
  `Invalid or expired link`. Теперь после проверки действительной ссылки
  возвращаются HTTP 409 и предложение войти в существующий аккаунт.
  До подтверждения владения email наличие аккаунта не раскрывается;
  прежний пароль сохраняется. Свидетельства приведены ниже.

## Экран успешной регистрации 30 октября 2026 года

После создания аккаунта в другом браузере страница показывает зелёную галочку
в круге по образцу `Device Authorized`, заголовок `Registration Successful`
и пояснение о возврате в приложение. Иконка появляется только после успешного
завершения регистрации; пароль очищается, форма скрывается. В светлой теме
зелёный цвет затемнён для контраста. Штатное продолжение исходного OAuth-входа
сохранено.

Кандидат: `f28831d19c71c74df620c1289715110ad336dbe3`, сервер
`0.80.0-aheadscale.email.3`. Проверка прежнего оформления дала ожидаемый
[RED](https://github.com/pomozoff/aheadscale-tests/actions/runs/41000364357):
после регистрации отсутствовал заголовок успешного завершения.
[Целевой браузерный прогон](https://github.com/pomozoff/aheadscale-tests/actions/runs/41000974330)
прошёл всеми семью группами. Получены и визуально проверены четыре снимка:
светлая и тёмная темы, 1024×768 и 390×844; горизонтального переполнения нет.
Browser plugin недоступен; использован существующий Playwright в Actions.
[Сборка только сервера](https://github.com/pomozoff/aheadscale-client/actions/runs/41000920248)
прошла. Опубликованные HTML/CSS/JS побайтно совпали с кандидатом; discovery,
Dashboard и закрытость API, целостность БД и сохранность данных проверены.
Новые письма при этом обновлении не отправлялись.

Ранее начатая проверка нового аккаунта на Ubuntu/Fedora не завершена:
владелец видел `Authorized` для Ubuntu, код Fedora истёк; обе CLI-попытки
завершились таймаутом без VPN-IP. Дополнительные профили недоступны в режиме
нативного NetworkManager. Временный обычный режим клиента отменён, прежние
профили и NetworkManager восстановлены, собственные неавторизованные профили
и временные настройки удалены. Этот этап не является PASS подключения ВМ.

## Сеть нового аккаунта 30 октября 2026 года

Ubuntu ARM64 и Fedora ARM64 зарегистрированы в новом аккаунте с подтверждённым
email. Принадлежность обоих устройств проверена по публичным ключам и связям
пользователь → аккаунт → устройства в рабочей БД. Закрытые ключи и токены
не читались; пароль вводил только владелец в браузере.

| --- | --- | --- |
| Каталог содержит другую тестовую ВМ | PASS | PASS |
| Приватное DNS-имя возвращает ожидаемый VPN-IP | PASS | PASS |
| Ping, три пакета | PASS | PASS |
| HTTP и проверка тела ответа по VPN-IP | PASS | PASS |
| HTTP и проверка тела ответа по приватному имени | PASS | PASS |

Ubuntu: `100.127.108.3`, `ubuntu-ahead.aheadscale.internal`.
Fedora: `100.127.191.77`, `fedora.aheadscale.internal`.
В каталоге также присутствовал отдельный узел профиля, созданного владельцем;
его не удаляли. Проверка чужой сети этим живым прогоном не выполнялась.

Для этой проверки временно включались дополнительные профили и обычный режим
клиента: нативный NetworkManager принудительно запрещает дополнительные профили.
Сначала Fedora завершила вход по коду. Код Ubuntu истёк; вход выполнен через
Connect в приложении, чтобы попытка начиналась в момент действия пользователя.
Отключение Fedora во время подготовки совпало с переключением на другой
профиль; возврат в авторизованный профиль восстановил Connected без нового входа.

После PASS восстановлены исходные службы с NetworkManager и прежние default-
профили. Авторизованные тестовые профили и профиль `yandex`, созданный владельцем,
сохранены; временные настройки в `/run` удалены. Оба HTTP-обработчика работали
только на VPN-IP и завершились после двух запросов; временных файлов не создавали.
Это приёмка регистрации, каталога, DNS и передачи данных для данной пары,
а не всей матрицы GUI/CLI, перезагрузок или системных VPN-переключателей.
