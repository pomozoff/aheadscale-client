# Windows VPN: подключение отдельного канала к движку

Дата: 20 октября 2026. **Согласованный этап подключения транспорта к движку проверен. Вся системная интеграция ещё не завершена.** Работа выполнялась одним агентом на Windows 11 ARM64 и Ubuntu ARM64.

Пользователь согласовал подключение канала после [положительного опыта 37](2026-10-20-windows-vpn-pipe-spike.md). AppService остаётся открытым на протяжении сеанса и обслуживает короткие управляющие запросы; IP-кадры передаются по отдельному постоянному двунаправленному именованному каналу.

## Что изменено

- Введён `PacketTransport`: явные права своего пользователя и своего AppContainer SID, низкая метка целостности, запрет удалённых клиентов, проверка фактического PID/пакета/токена и одноразового подтверждения сервера. Проверенные операции опыта 37 перенесены в общий компонент; разрешения существующего IPC Go-службы не расширялись.
- `native-config` передаёт параметры одноразового подключения через аутентифицированный AppService. Пакеты через старые `native-packet-in/out` больше не принимаются. Вложенный `ValueSet` допускается [контрактом платформы](https://learn.microsoft.com/en-us/uwp/api/windows.foundation.collections.valueset?view=winrt-26100).
- Независимые направления связывают `VpnChannel` с защищённым каналом существующего Go-движка. Размер IP-кадра ограничен MTU 1280, исходящая очередь — 256 кадрами. Ожидание отсутствующих данных прерывается отменой; частичный кадр и запись имеют ограниченное время ожидания.
- Посредник проверяет, что запущена именно опытная служба из своего установленного пакета. Завершение `Down` ожидается до освобождения блокировки следующего сеанса.
- При завершении движка посредник явно отключает свой RAS-профиль **до** закрытия управляющего соединения. Одного `VpnChannel.Stop()` оказалось недостаточно: Windows могла запустить новый сеанс после потери транспорта. Управление фиксированным собственным профилем вынесено в общий `session_controller.cpp`.

Это изменения опытного пакета. Установленный обычный клиент `.8`, его служебные файлы, ключи и регистрация не заменялись. Во время опыта путь службы временно переключался на отдельный бинарный файл с защищённым резервом настроек и автоматическим откатом.

Шесть проверок прошли на 38, затем на 39 после повторного подключения, затем повторно на 39 после настоящей остановки и запуска службы. Перед проверками имён сбрасывался DNS-кэш. Файлы hosts не изменялись.

На 38 отдельный длительный прогон выполнил семь успешных HTTP-запросов Ubuntu → Windows по полному приватному имени с интервалом 20 секунд; измеренная длительность — **123 секунды**, команда завершилась с кодом 0. Это проверка сохранения реальной связи, не измерение пропускной способности. Число 2344 кадра относится к отдельному синтетическому опыту 37 и не выдаётся здесь за счётчик реального движка.

## Отключение и восстановление

38 воспроизвёл дефект: после команды `Down`, использующей тот же RPC службы, что и текущий GUI, профиль снова был Connected и движок снова Connected. В журнале были `appservice-lost`, затем новое `native-channel-ready`; новый PID и более позднее время создания посредника подтвердили новый сеанс. Таким образом, передача пакетов уже работала, но намерение отключиться не сохранялось.

На 39 после добавления явного RAS Disconnect:

| Сценарий | Наблюдаемый результат |
| --- | --- |
| `Down` службы, тот же RPC-путь, что у текущего GUI | Профиль Disconnected, daemon Idle, адрес удалён, посредник завершился; дополнительное ожидание 12 секунд не выявило самоподключения |
| Повторный Connect системного профиля | Подключение восстановлено, шесть HTTP-проверок прошли |
| Системный Disconnect | Профиль Disconnected, daemon Idle; отключение сохранилось |
| Stop-Service Aheadscale при активном канале | Служба остановлена; системный профиль отключён, адрес удалён; повторного подключения при остановленной службе нет |
| Start-Service, затем Connect системного профиля | Connected, прежний адрес `100.88.77.246/16`, без повторной регистрации; шесть HTTP-проверок после восстановления прошли |

Фактические результаты: `native-pipe39-down-result.json`, `native-pipe39-lifecycle-result.json` и `native-pipe39-lifecycle-ready-action-result.json` (`success=true`). Общий кодек и контроллер сеанса: `go test -race ./client/internal/windowsvpn -count=1` — PASS.

Первый вариант проверки восстановления сравнивал состояние движка сразу после возврата RAS и получил промежуточное состояние. Последующая сверка подтвердила Connected без изменения кода; проверка исправлена на ограниченное ожидание одновременной готовности профиля и движка. Весь сценарий после этого завершился с кодом 0. Этот промежуточный неудачный прогон не засчитывался как PASS.

В первой Ubuntu-команде отсутствовал `rg`; проверка точных HTTP-ответов заменена встроенным `test` и повторена с кодом 0. Это был сбой подготовки проверки, а не результат сетевого теста.

## Состояние после опыта

- Восстановлена исходная служба `0.80.0-aheadscale.8`, Running/Connected; единственный исходный адрес `100.88.77.246/16` на `as0`. После возврата получен реальный HTTP 200 из Ubuntu с ожидаемым маркером и VPN-адресом отправителя.
- Обычный GUI запущен через задачу с правами Limited. Профиль `Aheadscale Prototype` оставлен Disconnected.
- Временные HTTP-сервисы Windows и Ubuntu остановлены. Правило firewall HTTP, задачи текущих опытов 38–39, задача автоматического отката и защищённый временный резерв удалены. Отсутствие слушателя HTTP в Windows подтверждено.
- `native-pipe39-cleanup-action-result.json`: `success=true`; `native-pipe39-cleanup-result.json` подтверждает исходную `.8`, Connected, `as0`, Disconnected опытного профиля и очистку.
- Пакет 0.1.39.1 и публичный сертификат оставлены для продолжения согласованного прототипа. Полное удаление пакета/доверия и повторная установка пока не считаются проверенными. Обновления Windows и перезагрузка ОС в этом этапе не выполнялись.

## Что ещё не завершено

Обычный GUI не пересобирался и его Connect ещё не направлен в контроллер системного профиля. Проверка `Down` охватывает тот же RPC службы, но не заменяет визуальный прогон настоящей кнопки. Попытка открыть значок через UI Automation не дала доступного элемента; визуальная проверка в этом этапе не засчитана.

Далее по задаче 4: платформенный адаптер кнопок Connect/Disconnect, проверка реальных переключателей обоих UI, отмены подключения и браузерного входа. По задаче 5 остаются настоящая перезагрузка native backend, полный цикл удаления/повторной установки и итоговая очистка пакета/сертификата. Отрицательные проверки другого пакета/пользователя подтверждены опытом 37; отдельный повтор на пакете 39 не выполнялся.

Публичного установщика с этой интеграцией пока нет; готовность всей системной VPN-интеграции не заявляется.
