# Windows 11 ARM64: повторная проверка Settings

На комплекте `.18` / MSIX `0.1.61.1` недоступность страницы Settings **воспроизведена и связана с выключенным виртуальным экраном**. При пробуждении дисплея тот же процесс сразу показывает страницу VPN; подключение Aheadscale не меняется. В этой серии требуется исправить условия UI-проверки, изменения клиента или питания компьютеров пользователей не нужны.

## Повторная диагностика: погасший экран

В 05:32 +03:00 исходная проверка снова дала отказ: у Settings PID `8652`, семь элементов UI без строки Aheadscale, `Responding=false`. Позднее все 20 потоков имели причину ожидания `Suspended`. Приведение окна на передний план и `IApplicationActivationManager::ActivateApplication` с успешным HRESULT не восстановили страницу. Свободно около 1,2 ГБ из 4 ГБ; ошибок активации Settings в проверенном журнале нет.

`GUID_CONSOLE_DISPLAY_STATE` показал **0 — дисплей выключен**. Разовый `SetThreadExecutionState(ES_SYSTEM_REQUIRED | ES_DISPLAY_REQUIRED)` дал переход **0 → 1**. Тот же PID `8652` перестал быть приостановленным, UI показал 84 элемента, Aheadscale и Disconnect. Перезапуск Settings, службы и VPN для восстановления не выполнялся.

Затем выполнены **два управляемых цикла без принудительного Resume**: события дисплея `1 → 0 → 1 → 0 → 1`. При Off строка Aheadscale и кнопка недоступны, видны 13 элементов оболочки; при On возвращаются 90 элементов, строка и доступная Disconnect. PID остаётся `8652`, системный VPN всё время Connected. Через несколько секунд Off потоки ещё не обязаны иметь `Suspended`: этот признак относится к исходному длительному простою, а не является обязательным условием отказа UI-проверки.

Поэтому нельзя считать заставку и отсутствие строки при выключенном дисплее доказательством сбоя VPN или взаимной блокировки Settings. Воспроизведение с включённым экраном и активным разблокированным сеансом будет отдельным отказом, который нужно диагностировать заново. Поведение других сборок Windows этим выводом не покрывается.

Документированное основание: [Microsoft: состояние и возобновление UWP-приложений](https://learn.microsoft.com/en-us/windows/uwp/launch-resume/suspend-an-app), [Microsoft: разовое пробуждение дисплея через SetThreadExecutionState](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-setthreadexecutionstate). Принудительный Resume пакета был отдельной диагностикой и сам по себе страницу не восстановил; режим отладки пакета не включался.

Свидетельства продолжения — подкаталог `diagnosis/`: исходный повторный отказ, состояния потоков и дисплея, два цикла, итоговая очистка. Восемь собственных задач удалены; VPN Connected, Defender и firewall включены. Постоянные настройки питания не менялись.

## Условия и результаты

- Windows 11 ARM64, build `26300`; исходник клиента `840c9a9b85b6fbb1a116e54eb88f1709d73d10dc`, тот же пакет, что в [предыдущем отчёте](2026-10-25-windows11-arm64-native-disconnect.md).
- При первой проверке до любых изменений видны строка Aheadscale, Connected и доступная кнопка Disconnect; процесс Settings отвечает. Сохранён снимок именно этого окна.
- Три новых запуска процесса Settings текущего пользователя: каждый раз открыты главная страница и затем VPN, найдены строка Aheadscale и доступная кнопка Disconnect. PID менялся `8644 → 3592 → 9112 → 8652`; все три проверки PASS.
- Реальная кнопка **Disconnect в Settings**: PASS. Служба Idle, системный профиль Disconnected, VPN-адрес отсутствует, ложных перезапусков интерфейса нет.
- **Connect в Aheadscale после системного отключения**: PASS. В конце служба, профиль и строка Settings показывают Connected, адрес `100.88.77.246/16`, callback 53000 не слушает.
- Defender, все профили firewall и постоянное UDP-правило службы включены. Собственные семь диагностических задач удалены.

Обновления, перезагрузка Windows, переустановка/сброс Settings, удаление VPN-профиля и повторная авторизация не выполнялись. Точечное завершение только своего SystemSettings использовано для трёх проверок нового запуска после уже успешной первой проверки; это не доказательство исправления исходного зависания.

Проверены видимость и обновление статуса строки, системный Disconnect и последующий Connect из приложения. Системная кнопка Connect, повторное измерение сетевого обмена, вся последовательность T02, перезагрузка и другие ОС этим прогоном не закрываются. Ранее сетевой обмен проверен в отчёте `.18`.

## RG29 и порядок повторной диагностики после первого прогона

Первый прогон дал **NOT_REPRODUCED / причина открыта**; последующая диагностика выше воспроизвела зависимость от состояния дисплея. Перед повтором сначала проверить включённый экран и активный разблокированный сеанс. Если зависание вернётся, сначала сохранить снимок только Settings, его PID/Responding, точную сборку, состояние профиля и события активации. Отдельно сравнить открытие `ms-settings:` и `ms-settings:network-vpn`. Проверять готовность по строке Aheadscale и доступной кнопке, а не только по наличию процесса. Не записывать успешный системный API как успешный UI-тест. Сброс пользовательских данных, удаление профиля и отключение защиты для этой проверки не нужны.

Первая попытка снимка была остановлена из-за координат окна вне допустимых границ; окно затем восстановлено в видимую область. В первом наблюдателе Disconnect промежуточный файл совпал с именем итогового файла: сам сценарий завершился успешно, что подтверждено отдельным `action-result` и проверкой конечных состояний. При очистке первая сверка ошибочно составленной квитанции остановилась до удаления; повтор использовал точные действия созданных задач. Эти отказы средств проверки сохранены отдельно от результатов приложения.

В первой управляемой серии наблюдатель дополнительно требовал немедленной приостановки потоков при Off; это условие не соответствует короткому выключению дисплея, и проверка остановилась. В повторе проверен сам симптом: состояние дисплея, доступность строки/кнопки, одинаковый PID и неизменный VPN; два цикла PASS. Исходная неудачная серия сохранена.
