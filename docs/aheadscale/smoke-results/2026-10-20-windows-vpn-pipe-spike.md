# Windows VPN: опыт с отдельным каналом передачи пакетов

Дата: 20 октября 2026. Статус: **PASS ограниченного опыта**, системная VPN-интеграция ещё не готова.

Пользователь согласовал проверку постоянного двунаправленного канала между Windows-плагином и посредником, с AppService для коротких управляющих запросов. Подключение канала к сетевому движку — следующий, отдельно обсуждаемый этап. Предыдущая диагностика описана в [основном отчёте](2026-10-19-windows-vpn-prototype.md).

## Условия

Windows 11 ARM64, собственный пакет `Aheadscale.VpnPrototype_9kyyx27wet2q6`. Плагин работает в AppContainer, посредник — как full-trust процесс того же пакета и пользователя. Исходная служба `0.80.0-aheadscale.8` продолжала работать через Wintun; переключения на опытный движок не было.

Для запуска настоящего VPN-хоста создан отдельный профиль `Aheadscale Pipe Probe` с адресом `192.0.2.1/32`, маршрутом `192.0.2.2/32`, без изменения DNS. Передавались только синтетические IPv4/ICMP-кадры длиной 28, 64, 511 и 1280 байт. Обе стороны независимо формировали ожидаемую последовательность и проверяли каждый байт принятого кадра.

Кадры шли через отдельный именованный канал. AppService передал параметры подключения и оставался открытым без передачи кадров до окончания потока. Это принципиальное условие успешного прогона.

## Ограничение доступа

Канал создаётся первым экземпляром, с запретом удалённых клиентов и явными правами своего пользователя и своего AppContainer SID; добавлена низкая метка целостности для AppContainer. Разрешения существующего IPC службы не менялись. Общего доступа Everyone или всем пакетам не добавляли.

Посредник сверяет пользователя, настоящий PID, принадлежность процесса своему пакету и точный AppContainer SID. Плагин проверяет PID сервера, полученный через аутентифицированный AppService, владельца канала и отдельный случайный nonce. Nonce и содержимое кадров в отчёт не включены. Это проверенный набор мер для опыта, а не утверждение о полном аудите безопасности.

Правила платформы: [IPC пакетных приложений](https://learn.microsoft.com/en-us/windows/uwp/communication/interprocess-communication), [права именованных каналов](https://learn.microsoft.com/en-us/windows/win32/ipc/named-pipe-security-and-access-rights), [обязательные уровни целостности](https://learn.microsoft.com/en-us/windows/win32/secauthz/mandatory-integrity-control).

## Очистка и оставшееся состояние

Очистка завершилась успешно; `pipe-spike37-cleanup-action-result.json` содержит `success=true`. Результат `pipe-spike-cleanup-result.json` подтверждает удаление тестового профиля, отрицательного тестового пакета, временного защищённого каталога и обеих временных задач. Исходная служба осталась `Running`, версия `0.80.0-aheadscale.8`, состояние `Connected`, адрес `100.88.77.246/16` на `as0`. Исходный GUI не заменялся.

Пакет прототипа 0.1.37.1 и его публичный сертификат оставлены для продолжения испытаний. Исходники опыта находятся в отдельной экспериментальной ветке `codex/windows-vpn-prototype`; подготовленные изменения основного рабочего дерева не заменялись. Обновления Windows, правила firewall и исключения loopback для этого опыта не настраивались.

## Следующий этап

Рекомендация: передавать пакеты через отдельный канал, сохраняя AppService как открытое управляющее соединение на время сеанса. До подключения к движку нужно явно согласовать управление временем жизни, отказ при неверном режиме/службе и единое состояние для системного VPN и приложения.

Этот опыт не проверяет реальный mesh-трафик, DNS, производительность, повторное подключение, перезагрузку, синхронизацию GUI или выпуск установщика. Исходное расхождение статусов Windows VPN и приложения ещё не считается исправленным; задачи 3–5 основного плана не закрываются результатом этого опыта.
