## Найденные проблемы и дальнейший контроль

1. **RG26: нет автоматического восстановления после перезапуска native-службы при живом UI.** Требуется повтор на исправленном комплекте без ручных Connect/up, с действующей регистрацией, Connect on Startup On, сохранением ключа и полным T01. Исправление в этом прогоне не выполнялось.
2. **Входящий TCP после ручного восстановления:** исходящие HTTP прошли, обратные — timeout. Тестовый Windows TCP-listener при этом ещё Running. Следующий контроль: локальный HTTP в Windows, затем перезапуск только своего ответчика с проверкой PID/startTicks и повтор; лишь отдельно проверять собственный фильтр интерфейса. Не менять одновременно ответчик, firewall и продукт и не объявлять причину установленной. Продуктовое UDP-правило не ослаблять. После полного reboot с новыми, локально проверенными ответчиками входящие и исходящие HTTP снова прошли; это не локализует предыдущий timeout и не закрывает RG26.
3. **Упаковка ARM64:** нужен единый native EXE и самостоятельная проверка его установки/обновления/удаления. Ручной запуск install-скрипта не снимает блокер.
4. **Оставшиеся случаи:** полный UI/CLI, стандартный CLI/Wintun ARM64 и отдельная CLI-установка, S07/прочие ветки R05/U02, полезные SSH/SFTP/RDP/SMB, изоляция/лимиты аккаунта, подтверждение email. Поддержка платформы целиком не объявляется.

## Ошибки наблюдателя и ограничения

Первая миграция завершилась успешно, но сборщик снимка завершился из-за BOM в склеенном операторском PS: это проверено по migration-result/keyPreserved, миграция повторно не запускалась. UIA Invoke для кнопки меню заменён поддерживаемым ExpandCollapse; для новых окон введено ожидание наличия контролов. Ошибки UIA фокуса/готовности не приписаны продукту; успешные снимки тем сохранены отдельно.

Первый CLI-наблюдатель прервался на ожидаемом stderr networks list у неподключённого клиента; после обработки exit code повтор в Connected завершён. В ходе длинного прогона истёк Ubuntu HTTP-ответчик: отказ сохранён, удалён только его собственный каталог по PID/UID/startTicks, создан новый ответчик. Попытка обновить Windows-ответчик ошибочно ожидала Ready, хотя задача ещё Running; этот отказ сохранён. Эти события не превращаются в PASS сети и не подменяют отдельный подтверждённый FAIL автоматического восстановления службы.

Первый post-reboot наблюдатель ошибочно считал отсутствие JSON недоступностью SSH: quser при отсутствии пользовательского сеанса вернул ненулевой результат. Проверка без quser подтвердила новый BootUpTime, SSH Automatic/Running и отсутствие explorer/UI. Это ошибка наблюдателя, не сетевой отказ ВМ. После пользовательского входа подтверждены автоматический запуск скрытого UI и восстановление сети; Первая попытка вернуть настройку через UIA не нашла окно: автозапуск оставил UI скрытым в трее. После сетевых проверок повторный запуск того же EXE вызвал штатный SingleInstance/ShowWindow, затем переключатель успешно возвращён в Off. Это открытие окна не использовалось как доказательство автозапуска.
