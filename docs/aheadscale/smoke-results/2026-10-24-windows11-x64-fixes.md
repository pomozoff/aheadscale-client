## Причины и изменения

1. **GUI exit 1 без окна.** Диагностический обработчик Wails зафиксировал
   nil-controller в `Chromium.SetBackgroundColour`: Theme менял фон до
   создания WebView2. Проверка одного манифеста, отдельного WebView-каталога
   и отключения GPU не устраняла исходное падение. Теперь каждое окно
   регистрируется до native Run; фон применяется после WindowRuntimeReady,
   а закрытое окно не оживляется поздним событием. Ошибки приложения
   направлены в клиентский logger.
2. **Иконки и сведения о файле.** Путь упаковки не генерировал syso UI.
   Добавлены собственные icon/manifest/info. Для Windows используется таблица
   сведений 0409: нейтральная 0000 давала пустые строковые свойства в .NET.
   Исправлен выбор x86-unicode ShellExecAsUser для 32-битного NSIS:
   прежний обход архива мог затереть его DLL другой архитектуры.
3. **SystemTemp / Access denied.** После завершения генерации и возможной
   загрузки служба выдаёт проверенному локальному SID чтение и удаление
   только готового файла. Защищённый DACL сохраняет SYSTEM/Administrators;
   каталог SystemTemp не открывается. CLI/UI обычным токеном копируют ZIP
   в собственный Temp, затем удаляют источник; Explorer больше не требует
   повышения прав. Загрузка во внешний сервис не запускалась.
4. **Strict пропускал IPv4.** Первый доступный ZIP `.9` показал исходные
   адреса в status.txt и network_map.json: не обрабатывались IPv4 соседа и
   адрес устройства с маской. Добавлено преобразование обоих полей через
   существующий anonymizer. В ZIP `.10` отсутствуют проверенные IP/имена
   обоих узлов и маркер PRIVATE KEY; архив цел и содержит 17 файлов.

## Перезагрузка

После `shutdown /r` RDP-клиент агента завершён; до восстановления VPN
нового входа не было. Ответ RDP проверялся как настоящий X.224 Connection
Confirm, отдельно через NAT и через VPN с Ubuntu. Консоль QEMU после
восстановления оставалась на экране блокировки.

| Событие | От начала наблюдения |
| --- | --- |
| VPN перестал отвечать | 21,82 с |
| NAT/RDP перестал отвечать | 28,29 с |
| NAT/RDP снова отвечает | 72,33 с |
| VPN/RDP снова отвечает | 110,75 с |

Разница после готовности NAT/RDP — **38,42 с**. Интервал недоступности VPN
около 88,93 с, поэтому общий бюджет T03 в 60 с по-прежнему **FAIL**.
Автовосстановление без входа пользователя функционально подтверждено.
После нового входа Windows служба Running/Auto, UI запущен автоматически из
Program Files, ключ/IP/FQDN прежние; все три HTTP A → B снова 200.
Наличие готового RDP не устанавливает момент готовности всей сети Windows;
причина оставшейся задержки требует отдельной диагностики. Настройки
повторов и таймауты наугад не менялись.

## Автоматические проверки

- `make test-unit` — exit 0, 243 пакета с тестами. Среда: Go 1.26.7,
  `TZ=UTC NETBIRD_STORE_ENGINE=sqlite GOMAXPROCS=4 GOFLAGS='-buildvcs=false -p=2'`.
  Это не полный PostgreSQL/MySQL matrix: прямые backend-тесты сохраняют
  свой выбор, общий helper проверен с явно выбранным SQLite.
- На самой Windows обычным токеном выполнены **пять** тестов DACL/экспорта,
  все PASS, без skipped: проверенный SID читает/удаляет и не получает запись;
  чужой SID не получает чтение; неподтверждённый caller отвергается;
  экспорт сохраняет байты и убирает источник; отсутствующий источник даёт ошибку.
- RED → GREEN: ErrorHandler; три сценария готовности Theme; имя архива;
  strict IPv4/CIDR. Первые ошибки и успешные повторы сохранены в закрытых
  журналах стенда.
- `bash -n packaging/aheadscale/build.sh`, компиляция package.py,
  `git diff --check` — PASS; реальная сборка NSIS `.10` завершена успешно.

Первый полный прогон выявил повреждённые ребрендингом DNS fixtures
(вход netbird.io, ожидание aheadscale.io), потерю UDP burst в маленьких
приёмных буферах теста и выход store-suite за 10 минут. Исправлены только
эти fixtures: согласованные example.com, размер буфера без снижения порога,
запоминание NETBIRD_STORE_ENGINE перед циклом. RED показал, что SQLite-selector
запускал также PostgreSQL/MySQL; GREEN — только выбранный SQLite.
В тестах agentnetwork сравнение временных отметок зависит от часового пояса;
прогон выполнен в UTC, как CI. Код production-БД этим не менялся.
