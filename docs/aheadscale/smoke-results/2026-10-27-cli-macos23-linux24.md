## C11: локальная диагностика Ubuntu

`debug bundle --anonymize-level strict` без sudo завершился с 0, но оставил ZIP с владельцем root и правами `600`: обычный пользователь прочитать его не смог. Этот путь не считается успешной выдачей архива обычному пользователю; требования к правам Unix-диагностики нужно отразить отдельно, защиту файла не ослабляли.

Повтор с sudo: корректный ZIP из 25 записей, проверка CRC успешна. В его содержимом не обнаружены известные исходные VPN IPv4/IPv6, FQDN и полные публичные ключи своего устройства и соседей. Аналогично проверен strict JSON status. Проверка сравнивает конкретные идентификаторы и **не доказывает отсутствие всех возможных секретов**. Изменение уровня логирования/persistence и полный C11 остаются открытыми. Флаг upload не передавался; архивы не отправлялись наружу и удалены из ВМ после проверки, включая архив первой непривилегированной попытки.

Всего четыре успешные T01-серии, **24 HTTP 200**. Каждый ответ содержит точный маркер получателя и наблюдаемый сервером VPN IP отправителя; адрес назначения curl тоже сверен. Запросы принудительно IPv4, без прокси, hosts или ручной подмены DNS. Это не измерение скорости подключения.

**RG40 — недоступен собственный VPN IPv4 macOS.** На `.22` и `.23` обращение macOS к слушателю на своём `100.88.213.250` получает TCP timeout. На `.23` обычный localhost с тем же обработчиком отвечает, а Ubuntu обращается к VPN-слушателю macOS успешно. ICMP к своему VPN IP: 0/2. В момент диагностики маршрут HOST/LOCAL вёл через utun120; это диагностический факт, а не доказанная причина. Маршруты, firewall и защиту ОС не меняли; исправления в этой работе нет. Этот случай выделен из успешного обмена между разными устройствами.

## Решения и следующие проверки

- По решению владельца **RG39 не исправлять**: up при Already connected может корректно сохранять действующие настройки. Наблюдение сохранено, но не считается подтверждённым дефектом или самостоятельным блокером выпуска.
- Следующий функциональный разбор — RG40: собственный VPN IPv4 macOS, отдельная регрессия и проверка безопасного исправления. Наличие Network Extension по-прежнему требует отдельного этапа и Apple Developer Program.
- Открыты RG38, чистый Linux CLI/headless-вход C03/C04, x64 Linux runtime, оставшиеся GUI/CLI/lifecycle, OS reboot macOS, изоляция аккаунтов, разные NAT и настоящий Relay. Windows в этом прогоне не проверялась.

После последней T01-серии Ubuntu и macOS были Connected с прежними ключами/IP/FQDN, GUI macOS восстановлен. При отдельной итоговой проверке обе ВМ перешли в NeedsLogin: сервер вернул PermissionDenied / peer login has expired. Ранее записанный sessionExpiresAt: Ubuntu `2026-10-27T03:41:23.623029495Z`, macOS `2026-10-27T03:41:58.710843526Z` (10:41 Asia/Krasnoyarsk); отказ получен после этих сроков, при проверке около 03:48 UTC. Это согласуется с истечением входа, а не доказывает потерю регистрации при обновлении или restart. Повторный вход и последующий сетевой контроль учитываются отдельно; правильность самой политики срока входа здесь не принималась. Все временные HTTP-процессы, PID/log-файлы и скопированный PKG удалены из ВМ. Сборок, CI-запусков и публикации не было; server/dashboard не изменялись.
