# Проверка Windows 11 ARM64 и связи с Ubuntu

Дата: 2026-10-19. Сценарии каталога и обмена данными взяты из
[плана проверок](../smoke-test-plan.md), S05/S06.

## Результат

Windows установлена и подключена к существующему аккаунту через браузер.
Windows и Ubuntu видят друг друга в каталоге, разрешают приватные имена и
передают HTTP-данные в обе стороны. Финальный прогон после перезапуска службы
Ubuntu: шесть запросов из шести вернули HTTP 200, правильный текст другого
устройства и его VPN IP. Соединение — P2P.

Первый сетевой прогон не прошёл: фактический порт WireGuard в Ubuntu отличался
от объявленного клиентом. Перед успешным прогоном порт исправлен вручную;
подробности ниже. Это ограничение результата, а не полный PASS установщиков.

Для проверки использовались отдельные HTTP-сервисы на TCP/8765, привязанные
только к VPN IP. В Windows временно разрешён входящий TCP/8765 только от VPN IP
Ubuntu. Firewall целиком не отключался. Windows-сервис тестового HTTP запускался
через интерактивное задание, чтобы его жизнь не зависела от SSH-сеанса.

## Обнаруженное расхождение порта Linux

До исправления клиент сообщал другому узлу порт 51830, а `wg show Aheadscale
listen-port` возвращал 51145. Профиль NetworkManager также содержал 51145.
Устройства обменивались STUN-пакетами, но рукопожатие WireGuard отсутствовало;
HTTP-запросы завершались тайм-аутом. Статус P2P сам по себе не доказывал обмен.

На тестовой Ubuntu выполнено `sudo wg set Aheadscale listen-port 51830`.
После очередного рукопожатия обмен Windows → Ubuntu заработал. Первый запрос
сразу после изменения ещё истёк по тайм-ауту; успех подтверждён отдельными
последующими запросами. После перезапуска службы обычная сборка `.7` сама
настроила 51830, сохранила регистрацию и прошла обмен в обе стороны.

Источник первоначального изменения порта не доказан; исходники клиента в этом
прогоне не менялись. Необходимо отдельно проверить сохранение настроек WireGuard
при обновлении DNS через NetworkManager, особенно после появления второго узла.
Флаг Reapply `preserve-external-ip` сохраняет внешние IP и маршруты; документация
не обещает сохранение порта WireGuard:
[NetworkManager Device.Reapply](https://networkmanager.pages.freedesktop.org/NetworkManager/NetworkManager/gdbus-org.freedesktop.NetworkManager.Device.html).
До повторяемого прогона без ручного исправления первоначальный сбой остаётся
открытым наблюдением.

## Прочие наблюдения и ограничения

- В Windows ярлык рабочего стола использует общий значок исполняемого файла.
  Собственный значок присутствовал в окне приветствия; дефект ярлыка не исправлен.
- Одна предыдущая попытка входа отменена операторским перезапуском GUI, что
  закрыло localhost:53000 до возврата браузера. В успешной попытке приложение
  и служба не перезапускались до завершения входа.
- Подтверждение владения email не включено; в этом прогоне использован готовый
  аккаунт. Повторная регистрация и отправка подтверждающего письма не проверялись.
- Разные интернет-подключения/NAT, принудительный Relay, HTTP по IPv6,
  перезагрузка Windows и Ubuntu целиком, обновление и удаление Windows-пакета —
  NOT_RUN. Этот прогон не заменяет полный базовый и расширенный smoke.

## Доказательства и очистка

Операторские материалы сохранены локально в `/tmp/aheadscale-windows`:
`install.ps1`, `final-windows-to-ubuntu.txt`, `final-ubuntu-to-windows.txt`,
`final-windows-state.json`. Полный JSON статуса и снимки экрана не включены в
репозиторий: они содержат метаданные устройств.

Оба HTTP-сервиса остановлены, каталог HTTP Ubuntu удалён, временное правило
Windows удалено. Порты 8765, 9222 и 9223 в Windows больше не слушаются.
Диагностический профиль Edge закрыт; обычные пользовательские вкладки не
закрывались. Уровни журналирования обеих служб возвращены к info.
Диагностические аргументы GUI удалены; для обычного запуска текущего GUI
оставлено одно задание без триггеров. Операторский SSH-доступ сохранён.
