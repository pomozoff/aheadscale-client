# Прототип системного VPN Windows

Статус: границы процессов и локальная передача пакетов подтверждены. Настоящий сетевой путь Windows VPN ещё проверяется; интеграция не готова к выпуску. Рабочий клиент `0.80.0-aheadscale.8` и регистрация устройства сохраняются.

## Среда и ограничения

Windows 11 ARM64 VM; второе устройство — Ubuntu ARM64. Windows: `100.88.77.246/16`, `win-s5jsuhs8ctr.aheadscale.internal`; Ubuntu: `100.88.19.208/16`, `ubuntu-ahead.aheadscale.internal`. Производственный сервер, аккаунты и ключи не изменялись. Старый Wintun не засчитывается проверкой нового системного канала.

Отдельные пакет `Aheadscale.VpnPrototype`, издатель `CN=Aheadscale VPN Prototype`, профиль `Aheadscale Prototype`. Подпись проверяется Windows; только публичный сертификат добавляется в TrustedPeople. Закрытый ключ NonExportable остаётся на runner и удаляется после подписи. Trusted Root, Defender, UAC и политика обновления не изменяются. Квитанция фиксирует только собственные объекты для удаления.

Следующий отказ — стадия start-channel, HRESULT `0x8000000E` («A method was called at an unexpected time»), без адреса и маршрута. ## Продолжение опытов 21–24

Назначенный UDP endpoint в 21 и флаг SplitTunneling в 22 пока не дали рабочего интерфейса. В 22 также проверен запуск после явного Down; гипотеза старой сессии не подтвердилась. RAS возвращал 628, адрес и маршрут отсутствовали. Пакеты по этому пути не передавались.

Схема дополнительных журналов Windows VPN проверена до их временного включения: только этапы, счётчики и LastError, без Binary/payload. В Operational зарегистрированы Connecting → Negotiating Network → Abort; в OperationalVerbose — входы Connect/Disconnect без событий завершения. После опыта первоначально выключенные журналы снова выключены.

В 23 устранена возможность блокировки между внешним Start и повторно входящим Disconnect: WinRT-вызовы выполняются без удержания delivery mutex, поздний результат Start отменяется. Это не подтвердило работоспособность: попытка снова завершилась RAS628. Сохранилась отметка перед ConfigureNativeChannel, однако пока нельзя приписывать отказ конкретно Start, поскольку построение маршрутов и DNS находится внутри этой функции. Исходная служба восстановлена.

Опыт 24 добавляет отдельные отметки внутренних этапов и проверку WinRT-коллекций перед разыменованием; проверяет документированный StartExistingTransports для уже назначенного через AssociateTransport сокета. Результат на VM ещё ожидается. Системный профиль, локальный обмен и компиляция по-прежнему не выдаются за готовую VPN-интеграцию.

Пакет 0.1.24.1 собран, подписан, установлен; опытная служба выбрана и Connect запущен. До получения результата MacBook с пробросом SSH перестал быть доступен (Tailscale Online=false, LastSeen `2026-10-19T18:10:00.1Z`); недоступны обе ВМ. Результат подключения 24 пока НЕИЗВЕСТЕН. Работоспособность или отказ этому пакету не присваивается. Перед опытом настроен автоматический возврат исходной службы через 10 минут. После восстановления доступа требуется сначала проверить фактическое состояние службы, профиля и интерфейса.


### 20 октября: минимальный IPv4-канал, пакет 0.1.25.1

Сборка `550ceb909b1cf2f0b9768aa8ffd59479a28adb18`, CI `39385427650` прошла. Вызов `StartExistingTransports` с IPv4 и маршрутами, без IPv6/DNS-параметров, вернулся успешно. Windows кратковременно назначила `100.88.77.246` интерфейсу `Aheadscale Prototype`; UDP transport получил локальный порт. Это подтверждает создание системного канала, но не готовность mesh.

Движок завершил запуск с `ICEBind has not been initialized yet`; перед этим журнал фиксирует закрытие relay, затем IP исчезает. Контроллер успел вернуть `Connected`, поэтому его ответ отдельно не считается PASS. HTTP и DNS: NOT_RUN. Повтор с подробным журналом воспроизводит отказ. В прототип добавлена запись первичных ошибок WireGuard в журнал службы и причин остановки системного канала; диагностическая сборка 26 запущена.

После каждого опыта исходная служба `.8` восстановлена с прежней регистрацией и адресом `as0`. Резерв восстановления содержит только настройки службы, ключи не копируются. Задача 3 остаётся незавершённой.


### 20 октября: первичный отказ обработки пакетов, пакет 0.1.26.1

Сборка `488af7be108bb614ed693536478926aca72a30c0`, CI `39386954141`: PASS. На реальной ВМ `native-encapsulate-error.json` зафиксировал `E_NOINTERFACE` (`0x80004002`), а первая причина остановки — `encapsulate-failed`. Журнал WireGuard подтвердил: bind открыт и состояние Up достигнуто, затем чтение TUN завершилось EOF, устройство закрыто; последующий Up проигнорирован для закрытого устройства. Ошибка ICEBind — вторичный эффект, повторная инициализация bind не исправляет первичный отказ.

Следующий опыт 27 проверяет гипотезу об интерфейсе перечисления `VpnPacketBufferList`: вместо range-for используются собственные RemoveAtBegin/Append; каждый взятый buffer возвращается исходному списку для штатной очистки Windows. Записываются поддержка IIterable и точная операция в обработчике. Поддержка буферов и передача реального трафика пока не подтверждены. Поведение очистки оставшихся buffers описано в [Microsoft IVpnPlugIn.Encapsulate](https://learn.microsoft.com/en-us/uwp/api/windows.networking.vpn.ivpnplugin.encapsulate?view=winrt-26100).


### 20 октября: пакеты 27–28, достигнут запуск движка

Пакет 27 (`fa55ce623627f323b1216208b25b1166c8c58be5`, CI `39387680067`) подтвердил отсутствие IIterable у фактического VpnPacketBufferList. RemoveAtBegin/Append устраняет первый E_NOINTERFACE. Следующий отказ: iface_guid_windows.go жёстко приводил backend к TunDevice; паника при инициализации DNS перезапускала службу. Регрессионный TestWindowsVPNGUIDBeforeChannelReturnsError воспроизвёл эту панику на настоящей Windows ARM64. После делегирования получения GUID активному backend этот тест и проверка выбора native backend прошли.

Пакет 28 (`fcbc28d61ff14339c2b53b39aabdb7aac545387e`, CI `39388495776`) собран успешно. Системный IPv4-адаптер и маршрут существуют, движок получает список устройств. Передача останавливается на send-packet с timeout; локальный pipe клиента открыт синхронно и одновременно используется для блокирующего чтения и записи. Опыт 29 меняет только модель I/O: FILE_FLAG_OVERLAPPED, отдельные событие и OVERLAPPED для каждой операции; отмена дожидается завершения перед освобождением памяти. [Контракт Microsoft для одновременных pipe I/O](https://learn.microsoft.com/en-us/windows/win32/ipc/synchronous-and-overlapped-input-and-output). HTTP пока FAIL, готовность mesh не подтверждена.

Дополнительно исправлен временный HTTP fixture Ubuntu: имя http.py скрывало стандартный пакет Python http. Сервис запускается с -I; собственный запрос Ubuntu вернул HTTP 200 и маркер с peer=100.88.19.208. Это проверка самого fixture, а не межмашинного VPN.

DNS в Windows пока не включён в параметрах VpnChannel. В applyDNSConfig получен отказ additional DNS domains — состав доменов требует отдельной проверки после рабочего IP-обмена.
