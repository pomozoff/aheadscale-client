Статус: граница процессов подтверждена; полноценная VPN-интеграция ещё не готова. Рабочий Aheadscale `.8` сохраняется. Строка профиля и локальный обмен пакетами отдельно не подтверждают рабочую частную сеть.

Windows 11 ARM64 VM, Aheadscale `0.80.0-aheadscale.8`, служба Running, `as0` с адресом `100.88.77.246/16`. Опытных профиля, пакета и сертификата не было. Сервер, регистрация и ключи не менялись. Установка выполняется в интерактивном сеансе: запуск Appx из SSH возвращал PLM `0x80070005`.

## Граница процессов

| Проверка на VM версии 0.1.8.1 | Результат |
| --- | --- |
| Настоящий вызов VPN Connect в AppContainer | PASS |
| Свой пакет → AppService → desktop → прежний RPC status | PASS: `probeStep=app-service-daemon-status`, `win32=0` |
| Другой подписанный пакет обращается к тому же AppService | PASS: Windows caller PFN отличается; `caller-rejected`, код клиента 1 |
| Остановка прежней Go-службы | PASS: `win32=2`, профиль Disconnected |
| Восстановление службы после проверки | PASS: Running, прежний IP `100.88.77.246` |
| Реальный IP-трафик через системный VPN | NOT_RUN |

Доказательство: операторский результат `vpn-auth-validation-results.json`; журнал плагина содержит только контекст и коды, без ключей и payload. Прямой AppContainer pipe достиг стадии открытия, но проверка desktop-идентичности вернула `ERROR_ACCESS_DENIED (5)`. Активный путь заменён AppService с проверкой предоставленной Windows CallerPackageFamilyName; исходные ACL службы не расширены.

После успешного status плагин намеренно возвращает `ERROR_NOT_SUPPORTED (50)`: до подключения настоящего пути пакетов профиль обязан оставаться Disconnected.

## Каталог Windows и перезагрузка

Профиль, созданный только через пакетный `VpnManagementAgent.AddProfileFromObjectAsync`, оказался в приватной `LocalState/rasphone.pbk` и не перечислялся обычным desktop `Get-VpnConnection`. После удаления только своего приватного профиля штатный `Add-VpnConnection` с `PlugInApplicationID` и обязательным `CustomConfiguration` создал системный пользовательский профиль. Его видят и `Get-VpnConnection`, и пакетный `VpnManagementAgent`.

Визуальная проверка Settings ещё NOT_CONFIRMED: приложение зависало на заставке. Пользователь разрешил перезагрузку, отдельно уведомлён о уже ожидающих перезапуска обновлениях. Команда перезапуска принята Windows; завершение и новая загрузка пока не подтверждены. Новые обновления вручную не запускались.

## Канал пакетов и оставшаяся работа

Узкие проверки Go-кодека и `tun.Device` прошли:

```text
go test ./client/internal/windowsvpn -count=1
go test -race ./client/internal/windowsvpn -count=1
```

Проверены точные байты в обе стороны `net.Pipe`, границы кадра 1–65535, длины 0/65536, короткие чтения, обрыв заголовка/payload, смещения буферов и разблокировка чтения/записи при повторяемом Close. Сетевые интерфейсы хоста не создавались.

Двоичный обмен настоящих Windows-процессов, новый Go backend, единственное владение адресами/маршрутами/DNS, управление из двух UI и шесть HTTP-проверок с Ubuntu остаются NOT_RUN. Исходники бинарной пробы подготовлены; сборка №39280648448 пока ждёт runner и не выдаётся за прошедшую проверку. Финальные перезагрузка с новым backend, удаление/повторная установка и откат также NOT_RUN.
