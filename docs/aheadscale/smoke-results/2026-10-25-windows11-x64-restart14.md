# Windows 11 x64: восстановление `.14` после перезагрузки

25 октября 2026. Проверен установленный закрытый preview `.14` / native MSIX `0.1.55.1` на QEMU/KVM Mac mini. Исходники клиента и конфигурация ВМ в этом прогоне не менялись. Это проверка перезапуска ОС для T03, не зачёт всей матрицы или всех веток T03.

## Комплект и условия

- Windows 11 Enterprise Evaluation x64 26300.9711, 2 vCPU / 8 ГБ RAM, UEFI/Secure Boot/TPM прежние.
- CLI, UI, служба — `0.80.0-aheadscale.14`; MSIX — `Aheadscale.VpnPrototype_0.1.55.1_x64__9kyyx27wet2q6`.
- Подписанный локальный исходник `e5ba355`, публичный snapshot `0ac4f72d7c006c397ec04b1f0286f505f153ec30`, [CI 40173691728](https://github.com/pomozoff/aheadscale-client/actions/runs/40173691728).
- Установщик и его SHA256 — в [отчёте о новом входе `.14`](2026-10-25-windows11-x64-single-login.md).
- Windows: `ahead-w11-x64.aheadscale.internal`, `100.88.12.187/16`. Ubuntu того же аккаунта: `ubuntu-ahead.aheadscale.internal`, `100.88.19.208/16`.
- Перед обоими перезапусками клиент и системный VPN Connected, продуктовая задача автозапуска включена; реестр не показывает ожидающего перезапуска обновлений.
- Оба раза Windows перезапускалась штатным `shutdown /r /t 0`, без принудительного закрытия приложений. Восстановление QEMU через остановку/холодный запуск не потребовалось.
- Для пользовательского сеанса использован обычный RDP-вход. Метрики сняты до ручного открытия GUI и без команды Connect или новой браузерной авторизации.

## Как измерялось время

Первый прогон проверил автоматическое восстановление и SSH/RDP. Его 41,67 с — время настоящего RDP-ответа через VPN, не измерение HTTP.

Для второго прогона подготовлены HTTP-ответчики только на VPN-адресах: Ubuntu `8765`, Windows `8766`. Маркеры — `aheadscale-smoke-peer-b` и `aheadscale-smoke-peer-a`. Временная задача Windows текущего пользователя с Limited/Interactive выполняла три HTTP-запроса к Ubuntu и лишь после их успеха запускала свой ответчик. Она не управляла подключением Aheadscale. Временное правило разрешало TCP 8766 только от `100.88.19.208` к `100.88.12.187` через Aheadscale для штатного PowerShell.

Наблюдатель на Ubuntu проверял системное разрешение полного и короткого имени Windows, HTTP 200, remote_ip и точное тело всех трёх ответов. Получение этих ответов после перезапуска подтверждает также предшествовавший успех трёх запросов Windows → Ubuntu. Локальный результат Windows сохранён повторно и его время проверено относительно новой загрузки: результат до перезапуска не использован как результат после него.

Все события доступности помечены одним монотонным таймером на Mac mini. Во втором прогоне первый ответ RDP от ОС — 121,02 с от старта наблюдения, завершение обратных HTTP-проверок — 172,64 с: разность 51,62 с. Проверки выполнялись с интервалом около двух секунд. Выбран первый ответ ОС; поздняя точка отсчёта для улучшения результата не подбиралась.

## Свидетельства и границы

- `login25-reboot14-http-before.json`, `login25-reboot14-http-timing.json`, `login25-reboot14-http-after-status.json`, `login25-reboot14-http-after-identity.json`, `login25-reboot14-http-logon.json` — второй перезапуск.

- `login25-reboot14-http-receipt.json`, `login25-reboot14-http-cleanup.json`, `login25-reboot14-http-ubuntu-receipt.json`, `login25-reboot14-http-ubuntu-cleanup.json` — владение временными ресурсами и очистка.

Сбой стенда при тёплом перезапуске `.13` остаётся историческим NOT_COMPLETED. На двух штатных перезапусках `.14` он не воспроизвёлся; причина прежнего сбоя этим не установлена. Отдельный перезапуск службы в составе T03 в данном прогоне не выполнялся. Полный UI/CLI, отрицательные runtime-проверки, остальные платформы и публичная подпись остаются самостоятельными условиями выпуска.
