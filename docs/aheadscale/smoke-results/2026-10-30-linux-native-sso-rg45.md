# Linux: источник второй записи и вход через браузер — 30 октября 2026

## Проверенный участок RG45

На Fedora ARM64 выполнен один обычный цикл NetworkManager Disconnect → Connect
с действительной регистрацией: повторный SSO не потребовался, UUID профиля,
VPN-IP и приватное имя сохранились. До и после — один профиль типа `vpn`.
Это вызовы штатного NetworkManager из пользовательского systemd, а не нажатия
графических кнопок; всю приёмку R05 таким результатом не заменяем.

Затем воспроизведено диагностическое переключение native → standalone → native.
В standalone NetworkManager обнаружил внешний WireGuard-интерфейс и добавил
временную запись типа `wireguard`, сохранив постоянный профиль типа `vpn`:
две записи с именем Aheadscale, но разными типами и UUID. Это источник второй
записи при смешении режимов тестирования, а не создание двух профилей плагином.
Появление временной записи после тестового переключения объясняет часть
наблюдений; задержка удаления строки в открытой панели отдельно не воспроизведена.

После возврата в native временная запись исчезла. Fedora Connected, прежние
IP/FQDN сохранены, временный drop-in удалён, исходные службы active. В модели
VPN-меню GNOME одна строка Aheadscale; меню в момент чтения скрыто, поэтому
это не снимок открытой панели и не полная визуальная приёмка.

Восстановление диагностического сценария дважды вернуло ошибку nmcli из-за
того, что постоянное подключение уже успело активироваться автоматически.
Статус Connected и единственный профиль проверены отдельно. Во время
standalone запуск основной службы автоматически запустил и native-controller
через зависимость unit; тот один раз отказал из-за временно выключенного
native-флага. Исходная зависимость и режим восстановлены. Эти ошибки
диагностического порядка запуска не считаются дефектом соединения продукта.

**Дальнейший порядок:** регистрацию других аккаунтов проверять в hosted fixture
или отдельных чистых гостях/снимках. Не отключать native-режим установленного
Desktop только ради дополнительного профиля. Настоящий Desktop ↔ CLI переход
проверять штатными согласованными пакетами, а не подменой одного ExecStart.
Не удалять профили по совпадению имени. RG45 остаётся открыт для отдельного
воспроизведения устаревшей строки панели в штатном режиме.

## Подтверждённый дефект внешнего таймаута SSO

Обе прежние регистрации потребовали нового входа. На Fedora журнал NM показал
`connect timeout exceeded` через 60 секунд, после чего остановился локальный
callback; браузер вернулся на уже закрытый localhost. В профилях `vpn.timeout=0`.
[Документация NetworkManager](https://www.networkmanager.dev/docs/api/latest/nm-settings-dbus.html)
определяет для нуля стандартный предел 60 секунд. Плагин при этом допускает
10 минут интерактивного SSO плюс отдельное время запуска движка.

На обеих тестовых ВМ оператор изменил только `vpn.timeout` собственного UUID
на 720 секунд; исходное значение — 0. На Fedora callback оставался доступен
после прежнего минутного предела, владелец завершил свежий вход, Connected
подтверждён по службе, интерфейсу и NetworkManager. Дополнительный обычный
Disconnect → Connect прошёл без нового входа.

Подготовлено исправление native-контроллера:

- Новый собственный профиль получает внешний бюджет 720 секунд.
- Существующий проверенный профиль с отсутствующим/нулевым значением обновляется
  без смены UUID и пользовательского имени; заданный ненулевой таймаут сохраняется.
- Проверки владельца, service-type, URL и интерфейса перед обновлением сохранены.
- Сроки токенов и внутренний срок SSO не увеличиваются.

[RED 41012028767](https://github.com/pomozoff/aheadscale-client/actions/runs/41012028767):
обе новые регрессии подтвердили отсутствие бюджета и миграции. В тестовом
D-Bus fixture дополнительно обнаружена гонка при выдаче изменяемой карты;
ответ теперь копируется под блокировкой перед передачей асинхронному encoder.
[GREEN 41012640961](https://github.com/pomozoff/aheadscale-client/actions/runs/41012640961):
`native-controller` и `plugin-protocol-dbus` PASS с race detector.
Проверенный исходник `56d1e1c`; `223d574` меняет только оформление константы.
Рабочая ветка — `codex/linux-native-networkmanager`.

Исправленный контроллер ещё не выпущен установщиком и не заменял бинарники ВМ.
На ВМ действует описанная операторская настройка профиля; это не доказательство
автоматической миграции установленным новым пакетом. Полная live-приёмка
native-функции и перенос её кода в main ещё не завершены.

## Ubuntu Plasma: запрос входа блокируется настройкой KWallet

После увеличения таймаута callback запускается, но новая вкладка не открывается.
Короткая диагностика `plasma-kded6` показала: запрос с SSO-подсказками и флагами 5
получен, агент остановился на `Waiting for the wallet to open`. Ссылки,
подсказки с токенами и пароли в отчёт не записывались.

В этом стенде Plasma установлена поверх Ubuntu с другим рабочим столом.
Хранилище KWallet ещё не создано. Журнал backend содержал
`createDLGroup failed: maybe libqca-ossl is missing`; пакет `libqca-qt6-2`
присутствовал, а `libqca-qt6-plugins` отсутствовал. Установлен только
`libqca-qt6-plugins` версии `2.3.10-2` для ARM64, без обновления остальных
пакетов. Уже запущенный `ksecretd` сохранял прежний список провайдеров:
одного перезапуска `kded6` и совместимого `kwalletd6` было недостаточно.

После завершения только пользовательских процессов `kwalletd6`/`ksecretd`
и перезапуска `plasma-kded6` новый backend загрузил `qca-ossl`.
При следующем запросе появился штатный мастер создания `kdewallet`.
Пользовательская D-Bus-служба, GNOME Keyring и системные политики безопасности
не перезапускались и не отключались. Временная настройка подробного журнала
удалена. Регистрация устройства и профили не удалялись.

Владелец завершил мастер с зашифрованным хранилищем. После создания файла
backend `ksecretd` показывал `Locked=false`, но уже запущенный совместимый
`kwalletd6` всё ещё возвращал `isOpen=false`; новая попытка SSO ждала KDE.
В этом смешанном сеансе также работает GNOME Keyring: его отдельная связка
`login` была заблокирована. Владелец разблокировал её через штатный запрос.
Само это действие не исправило `isOpen=false` у совместимого KWallet.

После перезапуска только пользовательского совместимого `kwalletd6` и агента
`plasma-kded6`, с сохранением открытого backend и хранилищ, `isOpen` стал true,
модуль `plasmanetworkmanagement_aheadscaleui` загрузился. Callback свежей попытки
слушал порт 53000. Владелец завершил браузерный вход и подтвердил Connected.
Регистрации, профили и пароли не удалялись; защиту хранилищ не отключали.

[Архитектура KWallet](https://github.com/KDE/kwallet/blob/v6.24.0/README.md)
разделяет совместимый API `kwalletd` и Secret Service backend.
Не следует отождествлять наличие файла `.kwl`, открытое хранилище backend
и готовность клиента совместимого API. Наличие GNOME Keyring в этом сеансе
подтверждено; необходимость его разблокировки для чистой установки KDE
этим прогоном не доказана.

### Результат свежего входа и сети

Проверены установленные пакеты `.31.6` с бинарниками `.31`, основной профиль
`default` на обеих ВМ. Ubuntu: Management/Signal Connected, VPN-IP
`100.88.19.208`, имя `ubuntu-ahead.aheadscale.internal`. Fedora:
Management/Signal Connected, VPN-IP `100.88.54.63`, имя
`fedora.aheadscale.internal`. На обеих — один профиль Aheadscale типа `vpn`,
активный через `enp0s1`; UUID и адреса сохранены.

В обе стороны приватное имя разрешилось в ожидаемый VPN-IP; по два ICMP-пакета
доставлены без потерь. TCP-подключение к SSH-порту 22 по приватному имени
в обе стороны получило штатный SSH banner. Это проверка реальной передачи
данных через VPN, без SSH-аутентификации, чтения чужих файлов и временных
серверов или правил firewall. Браузерный вход Ubuntu и этот сетевой smoke
**PASS**. Показатель CLI `Nameservers: 0/0` не помешал разрешению приватных имён.

Для чистого KDE в дальнейшей приёмке проверять не только действующую
регистрацию, но и первый вход с ещё не настроенным либо закрытым системным
хранилищем. Установка `libqca-qt6-plugins` на одном смешанном стенде не доказывает
необходимость новой зависимости для всех Linux-установщиков. Подключение
исправленного установщика с автоматическим бюджетом 720 секунд и RG45
для открытой панели остаются отдельными незавершёнными проверками; этот smoke
не закрывает всю RG46, reboot или матрицу Linux.

## Границы результата

Установщики, reboot, остальные ОС и полная матрица не запускались. Закрытый
GUI-исполнитель Actions ещё не готов; live-диагностика ВМ выполнена напрямую.
В Actions выполнялись только существующие целевые NetworkManager-проверки,
без сборок приложений, установки SDK на Mac mini и реальных почтовых отправок.
