# Fedora ARM64: подготовка нативных RPM

Дата: 21 октября 2026. Работа выполнена одним агентом.

## Состояние

**Desktop `.8`: установка и обновление Fedora/Ubuntu, регистрация, приватный DNS, HTTP в обе стороны, перезапуск служб и цикл GUI — PASS. Полный smoke ещё не завершён: загрузка ОС, удаление и отдельный CLI-прогон остаются NOT_RUN.** Windows после новой настройки автозапуска тоже ещё не перезагружалась: команда не была доставлена по SSH. Предыдущий ручной запуск GUI после перезагрузки не считается проверкой нового автозапуска.

## Что изменено

- В существующем `package.py` добавлен формат `--format rpm`; прежний DEB остаётся по умолчанию.
- `build.sh linux arm64 public rpm` выбирает RPM для desktop и CLI. Три прежних аргумента сохраняют DEB; команды Windows/macOS не менялись.
- Нативный RPM содержит собственный vendor unit `aheadscale.service`, стандартные макросы systemd, отдельные зависимости Fedora, лицензию и notices. Desktop включает GUI и службу одним пакетом. CLI — `aheadscale-cli`, без графических библиотек; варианты исключают одновременную установку.
- Unit использует прежние адрес IPC и каталог регистрации `/var/lib/aheadscale` с доступом root. При удалении конфигурация и ключи сохраняются. Очистка NetworkManager затрагивает только точные runtime-правила Aheadscale.
- Локальный `/etc/systemd/system/aheadscale.service` останавливает установку до изменений: неизвестный unit не перезаписывается. NetBird/Tailscale, SELinux и firewalld не меняются.

Это нативная RPM-упаковка готовых ELF со своими unit и scriptlets. Бинарники взяты из проверенной сборки `.7`; их повторной компиляции и механической конвертации DEB через alien не было. Публичный сервер в бинарниках — aheadscale.ru. Это артефакты для собственных испытаний, обычная публикация/CDN не выполнялись; RPM пока без релизной подписи.

Первый rpmbuild остановился на конфликтующем с архитектурой сборщика явном BuildArch. В spec оставлен штатный выбор архитектуры через `--target`; готовые пакеты действительно имеют aarch64. Проверки архитектуры не отключались. Первое сравнение DEB ошибочно ожидало 0755; исходный `.7` уже имел 0775. Повтор сравнивал новый DEB непосредственно с исходным архивом и подтвердил полное совпадение, включая 0775. DEB-права этим изменением не менялись. RPM нормализовал их до 0755. В сборочном журнале есть предупреждение о пустом changelog для source_date_epoch; это не ошибка упаковки и не подтверждение воспроизводимой релизной сборки.

## Следующий прогон на Fedora

На чистой ARM64 ВМ установить desktop RPM через `sudo dnf install ./aheadscale_0.80.0-aheadscale.7_linux_arm64_public.rpm`, чтобы штатный менеджер разрешил зависимости. Затем выполнить [общий smoke-план](../smoke-test-plan.md): вход, настоящий обмен с Ubuntu по IP/полному/короткому имени, оба состояния интерфейса, перезагрузка и удаление. Установку с SELinux/firewalld надо проверять с их исходными настройками. Пакет сам правил безопасности не меняет.

Для повторной упаковки готовых бинарников используется `python3 packaging/aheadscale/package.py --platform linux --arch arm64 --channel public --version 0.80.0-aheadscale.7 --format rpm`; нужны rpmbuild и systemd-rpm-macros, а также новый, не использованный ранее staging. Полная компиляция через build.sh на Fedora в этом этапе отдельно не запускалась. Автоматическая замена desktop и CLI друг на друга одной транзакцией также не проверялась.

Имена библиотек проверены по [официальному пакету WebKitGTK](https://packages.fedoraproject.org/pkgs/webkitgtk/webkitgtk6.0/); макросы — из установленного [systemd-rpm-macros](https://packages.fedoraproject.org/pkgs/systemd/systemd-rpm-macros/index.html). Сборочные журналы и подробные результаты сохранены в `/tmp/aheadscale-fedora-rpm/`.

## Первый запуск на Fedora 44 ARM64

Фактическая ВМ: Fedora release 44, aarch64, GNOME Shell 50.0, Wayland, NetworkManager 1.56.0. GTK 4.22.1 и WebKitGTK 2.52.1 уже установлены. SSH-ключ сверён с отпечатком, который владелец получил в консоли; доступа по паролю агент не использовал. Прямой Tailscale Serve с MacBook принимал TCP, но не передавал SSH-ответ. После локального SSH-туннеля на MacBook и направления Serve на localhost ключ и вход успешно проверены.

- Desktop RPM передан в Downloads, SHA256 совпал с таблицей выше. `dnf install` выполнен с отключёнными репозиториями: установился только локальный Aheadscale, загрузка зависимостей и обновление ОС не потребовались. DNF сообщил, что OpenPGP-проверка локального неподписанного preview пропущена; это не проверка релизной подписи.
- `rpm -V aheadscale` — exit 0. Служба enabled/active/running, ExecMainStatus=0; CLI сообщает `.7`. Все динамические библиотеки GUI найдены. Пользовательский GNOME-сеанс действительно содержит процесс и окно Aheadscale; это подтверждено systemd и AT-SPI, не только успешной командой запуска.
- Launcher находится в `/usr/share/applications/org.wails.aheadscale.desktop`: Name=Aheadscale, Icon=aheadscale, Exec=/usr/bin/aheadscale-ui. Первоначальная диагностическая попытка прочитать `aheadscale.desktop` использовала неверное имя файла; это не отсутствие установленного launcher.
- Владелец выполнил браузерный вход в свой аккаунт и подтвердил Connected. Служба независимо подтвердила connected для Management/Signal на aheadscale.ru и адрес `100.88.185.206/16`, имя `fedora.aheadscale.internal`.
- Фактическое имя Linux-интерфейса — `Aheadscale`, тип WireGuard. NetworkManager сообщает connected (externally), активное подключение называется Aheadscale. В каталоге есть Ubuntu и Windows тестового аккаунта; это ещё не доказательство обмена с ними.
- SELinux сохранил Enforcing, firewalld, NetworkManager и systemd-resolved активны. В просмотренном недавнем audit-журнале AVC нет. `/var/lib/aheadscale` имеет root:root 0700. Никаких отключений SELinux/firewalld для установки не выполнялось.
- В GUI-журнале есть предупреждения EGL/Mesa гостевой графики; процесс и окно при этом работают. Полная визуальная проверка контраста/значков и настоящий сетевой обмен ещё требуют завершения.

Проверка `resolvectl status as0` сначала адресовала неверное имя интерфейса; дальше используется фактическое имя Aheadscale. Собственное имя Fedora через NSS возвращает как LAN, так и VPN-адрес; это отдельно от обязательной проверки приватных имён другого устройства.

## Локальный цикл подключения и приватный DNS

- `resolvectl status Aheadscale` подтверждает DNS-сервер на VPN-адресе Fedora, домен `aheadscale.internal` и DefaultRoute=no. `getent ahostsv4` разрешает полное и короткое имя Ubuntu в `100.88.19.208`, а Windows — в `100.88.77.246`.
- Отключение выполнено доступным пользователю переключателем GUI через AT-SPI. Служба перешла в Idle, VPN-адрес пропал, активное подключение Aheadscale исчезло из NetworkManager. Обычный DNS aheadscale.ru продолжает работать.
- В журнале NetworkManager переход имеет reason=user-requested, затем устройство удаляется. В просмотренном интервале для Aheadscale нет activation failed/connection failed. Визуальное отсутствие уведомления GNOME отдельно не заявляется.
- Тем же переключателем GUI соединение включено обратно. Проверка статуса и идентичности устройства выполняется отдельно; не считать успешное нажатие кнопки доказательством Connected.
- Первый обмен с Ubuntu/Windows не прошёл: ping и SSH по VPN-адресам дали тайм-ауты, WireGuard handshake отсутствовал. На этот момент и старые LAN-адреса обеих ВМ не отвечали. После этого владелец запустил Ubuntu и подтвердил Connected; повторная проверка необходима. Этот неуспешный результат не удаляется и не объявляется проверкой работоспособной пары.

## Найденный дефект WireGuard-порта

После появления рабочей Ubuntu в каталоге ICE показывал P2P, но WireGuard handshake оставался нулевым и полезный трафик не проходил. Это отдельный дефект, а не подтверждение выключенных ВМ.

- На Fedora CLI сообщал 51830, тогда как `Device.WireGuard.ListenPort`, NetworkManager и UDP-сокеты ядра показывали 35010. После перезапуска службы регистрация и Connected сохранились, но ядро слушало уже 51404. Публичный ключ ядра совпадал с зарегистрированным; закрытые ключи для диагностики не выводились.
- На Ubuntu `.7` аналогично: заявлено 51830, фактически 41443. SSH к ней удалось установить по подтверждённому LAN-адресу 192.168.1.156 через Fedora, с исходным проверенным ключом.
- Только после временного применения `wireguard.listen-port=51830` к обоим собственным активным устройствам заработали ping по IPv4, полному и короткому имени Ubuntu. Имена выбрали приватный IPv6; потерь в трёх пакетах каждого запроса нет. Статус подтвердил настоящее новое WireGuard-рукопожатие и ненулевой RX. Firewall для этого не изменялся.
- Ручная корректировка подтверждает причину, но не считается исправлением устанавливаемого клиента: при следующем старте проблема воспроизводится. После перезапуска нужно автоматически сохранять фактические параметры транспорта при DNS Reapply.

В [официальном исходнике NetworkManager 1.56.0](https://github.com/NetworkManager/NetworkManager/blob/1.56.0/src/core/devices/nm-device-wireguard.c) Reapply вызывает настройку WireGuard, включая listen-port и fwmark. Перед передачей DNS-настроек необходимо перенести в применяемый снимок фактические значения собственного интерфейса из ядра, сохранив остальные настройки и не копируя закрытый ключ. На этом этапе исправление ещё было в работе. Проверенные результаты `.8` приведены ниже.

GNOME Settings дополнительно проверены через AT-SPI: на странице Network присутствует список VPN и элемент Aheadscale. Это подтверждает наличие элемента в настоящем системном UI; полный визуальный аудит значков не выполнялся.

## Результат исправления `.8`

Выполнены регрессионные тесты, собрана только исправленная ARM64-служба и обновлены обе ВМ: native RPM на Fedora и DEB на Ubuntu. GUI `.7` сохранён без пересборки. После обновления и отдельного перезапуска обеих служб автоматически сохраняются UDP 51830 и routing mark 114176. Публичные ключи, адреса и имена устройств прежние, повторный вход не понадобился.

12 HTTP-запросов по IP/FQDN/короткому имени в обе стороны прошли после обновления и после перезапуска. После выключения/включения Fedora переключателем GUI прошли ещё два запроса. Проверяются точные маркеры удалённой ВМ и VPN remote_ip; это не просто Connected/P2P. Временные HTTP-службы остановлены, их файлы удалены. Оба клиента оставлены подключёнными.

Пакеты `.8`, SHA256, исходный снимок и ограничения — в [отдельном отчёте исправления](../2026-10-21-linux-wireguard-port-fix.md). CLI-пакеты упакованы, но отдельно не устанавливались. Первая попытка apt с `--no-download` завершилась внутренней ошибкой пути до установки; локальный dpkg завершил обновление без загрузок и без изменения системных пакетов.
