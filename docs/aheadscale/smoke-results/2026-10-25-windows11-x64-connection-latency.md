# Windows 11 x64: разбор времени подключения `.14`

25 октября 2026. Задача — отделить повторный Connect на прогретой ОС от прежних 40+ секунд восстановления после reboot. Продуктовый код, установщик, DNS и конфигурация защиты не менялись. Методика — [P01–P06](../connection-performance-test-plan.md); исходный комплект — [`.14` / native 55](2026-10-25-windows11-x64-single-login.md).

## Вывод

**40+ секунд на прогретых ОС и UI в этой серии не воспроизвелись.** Три нажатия Connect дали Connected за 5,725–8,823 с, первый HTTP по VPN IP — за 5,961–9,079 с. Три последовательных исходящих HTTP по IP, полному и короткому имени завершились за 9,250–12,893 с. Обратное направление в этой серии не измерялось: это диагностика клиентской задержки, **не полный PASS P01/T01**.

В историческом reboot-замере время включало вход пользователя и запуск UI. Во втором перезапуске между созданием процесса UI и началом native-команды прошло 24,262 с; сама команда заняла 13,172 с. На тёплом Connect эта команда занимала 5,375–7,578 с. Отдельно короткое имя добавляет 2,809–2,922 с разрешения DNS даже при уже работающем соединении.

## Стенд и метод

- Windows 11 Enterprise Evaluation x64 26300.9711; QEMU/KVM на Mac mini, 2 vCPU / 8 ГБ RAM. ОС, пользовательский сеанс и UI уже работали; новая установка/перезагрузка для тёплой серии не выполнялась.
- CLI/UI/служба `0.80.0-aheadscale.14`, native MSIX `0.1.55.1`; исходник `e5ba355`, [CI 40173691728](https://github.com/pomozoff/aheadscale-client/actions/runs/40173691728). UI SHA256 `821DCF629CEC3EEEB2DC7BA74B0EC7736C9B16D00391B3056D874C7CAA4DEB4D`.
- Зарегистрированный Windows `100.88.12.187/16`; Ubuntu `.8`, `100.88.19.208/16`, `ubuntu-ahead.aheadscale.internal`. Маршрут Relay, новая браузерная авторизация не требовалась. После каждой попытки проверены прежние адрес и SHA256 публичного ключа устройства.
- Действие выполнял UI Automation TogglePattern существующей кнопки `Toggle Aheadscale connection`, UI PID 5516, обычный пользователь. Наблюдатель с правами администратора собирал процессы и диагностические файлы; он не вызывал отдельные Connect, `up`, Login или `down`.
- До каждого Connect: штатный UI Disconnect, ожидание Disconnected **и завершения прежнего broker**, затем 2 с покоя. Отключение занимало 5,484–5,611 с и не включено во время нового Connect. Немедленный повтор во время cleanup (P02) не проверен.
- HTTP-ответчик Ubuntu слушал только VPN IP:8765, `/probe.txt`, точное тело `aheadscale-latency25-peer-b\n`. Проверены HTTP 200, remote_ip и тело; прокси отключён. После первого успеха IP последовательно проверялись FQDN и короткое имя. Это измеряет завершение последовательной проверки, не одновременную готовность трёх адресов.
- Время от действия — Windows Stopwatch. В начале подключения IP-запросы имели connect timeout 1 с / total 2 с; после готовности FQDN/short — 5/8 с. UI опрашивался в том же цикле: его время является первым наблюдением и может запаздывать из-за выполняющегося запроса. Неуспешных IP-проб до готовности: 3, 3 и 4.

| --- | --- | --- | --- | --- | --- |
| 1 | 7,200 | 7,468 | 7,738 | 10,882 | PASS |
| 2 | 5,725 | 5,961 | 6,191 | 9,250 | PASS |
| 3 | 8,823 | 9,079 | 9,652 | 12,893 | PASS |
| Минимум / медиана / максимум | 5,725 / 7,200 / 8,823 | 5,961 / 7,468 / 9,079 | 6,191 / 7,738 / 9,652 | 9,250 / 10,882 / 12,893 | Полный P01 не зачтён |

Системный профиль по окончании каждой попытки Connected. Нулевые exit code и правильные ответы подтверждены; старый результат до действия за новый не выдавался. Трёх попыток недостаточно для p95 или обещания времени на всех компьютерах.

### Где тратится время внутри Connect

| Попытка | Действие → начало native-команды | Действие → Up демона | Up → engine started | Вся native-команда | Внутри неё channel enter → ready |
| --- | --- | --- | --- | --- | --- |
| 1 | 0,765 | 4,109 | 2,701 | 6,844 | 2,179 |
| 2 | 0,576 | 2,989 | 2,219 | 5,375 | 1,944 |
| 3 | 1,349 | 5,471 | 2,635 | 7,578 | 2,267 |

Столбцы **перекрываются**, их нельзя складывать. Время native-команды взято из `elapsedMs`; границы Up/engine — из журнала того же Windows. Время stage JSON — файловый LastWrite UTC, приближённый к записи события. Разница старта/окончания этих файлов поэтому немного отличается от `elapsedMs`.

Процессы подтверждают цепочку UI → controller → штатный PowerShell (`Get-VpnConnection`, `rasdial`) → пакетный VPN-компонент/broker → `aheadscale up --no-browser` → движок/канал. Сам демон получает Up только через 2,989–5,471 с после действия. Это измеренная задержка **до движка**, а не 40 секунд сетевого согласования WireGuard или ожидания management. WMI ProcessStartTrace даёт сгруппированные времена примерно с секундной точностью; им подтверждены состав и родительские PID, но не миллисекундная стоимость каждого запуска процесса.

### Отдельная задержка короткого имени

`curl.exe` с системным DNS показал следующие `time_namelookup`:

| Адрес | Попытка 1 | Попытка 2 | Попытка 3 |
| --- | --- | --- | --- |
| IP | 0,000178 | 0,000192 | 0,000185 |
| FQDN | 0,029506 | 0,025368 | 0,059972 |
| Короткое имя | 2,823419 | 2,808862 | 2,921760 |

После готовности полный HTTP по IP занимает 0,168–0,194 с, по FQDN — 0,190–0,298 с, по short — 3,019–3,116 с. Контрольный запрос на уже подключённой сети также дал около 2,82 с DNS для short. У адаптера и VPN-профиля суффикс `aheadscale.internal` установлен, глобальный SuffixSearchList пуст. Отсутствие суффикса этим не подтверждается; конкретный порядок/ретраи системного резолвера без трассировки DNS не установлен. Причину нельзя объявить исправленной добавлением суффикса наугад.

Первая подготовительная проверка была остановлена **до Disconnect**: наблюдатель выделил short всего 2 с и получил timeout. Это ошибка настройки измерителя, сохранённая отдельно в `latency25-warm-setup-error.json`. После увеличения тайм-аута предварительная проверка и все три подключения прошли. Этот отказ не удалён из истории и не приписан продукту.

## Почему раньше получилось 40+ секунд

[Отчёт о двух reboot](2026-10-25-windows11-x64-restart14.md) содержал два разных измерения: 41,67 с до ответа RDP через VPN и 51,62 с до завершения шести HTTP. Оба отсчитывались от первого ответа **обычного RDP ОС**. Этот момент предшествует входу и не означает, что Aheadscale UI уже готов.

Во втором reboot сохранённая трасса позволяет выделить следующие границы; времена в UTC:

| Событие | Время / длительность |
| --- | --- |
| Создан UI-процесс | 08:23:53,337; через 1,366 с после входа Windows |
| Начало native-команды | 08:24:17,599; **24,262 с после создания UI** |
| Зарегистрирован broker / подтверждён владелец pipe | 08:24:25,945 / 08:24:26,752 |
| Up демона / engine started | 08:24:26,512 / 08:24:29,808; участок **3,296 с** |
| Native channel enter / ready | 08:24:27,126 / 08:24:29,899 |
| Окончание native-команды | файл 08:24:30,596; её монотонный `elapsedMs` **13172** |
| Завершены три Windows → Ubuntu HTTP | 08:24:36,276 |

Основные измеренные участки после создания UI — 24,262 с до запроса и около 13,172 с native-команды. Последняя включает движок/канал; добавлять ещё 3,296 с сверху неправильно. Пользовательский вход и проверки имён/ответов добавляются к общей точке отсчёта ОС/RDP. Это объясняет состав прежней длинной метрики, но не воспроизводит каждую её секунду и не устанавливает причину каждой внутренней паузы.

В исходниках `client/ui/main.go` восстановление запускается после ApplicationStarted. `Connection.ResumeOnLaunch` последовательно получает клиента демона, активный профиль и конфигурацию, затем вызывает StartOnLaunch. Отдельных временных меток этих шагов в сохранённой трассе нет: **24,262 с локализованы до native-команды, но не разделены на инициализацию UI, RPC и активацию пакета**. Называть причиной только WebView, антивирус, сервер или загрузку CPU нельзя.

Лимит ожидания cleanup 30 с в `windows_vpn_controller_windows.go` применяется при ещё работающем предыдущем broker; native-команда имеет лимит 60 с, канал — ограниченные ожидания готовности. Это верхние границы, а не фиксированные задержки: тёплые замеры не показывают обязательного ожидания 30/40/60 с.

## Что проверять и оптимизировать следующим

1. **Первый запуск UI на уже работающей ОС (P03):** поставить монотонные отметки создания процесса, ApplicationStarted, входа/выхода каждого RPC ResumeOnLaunch, активации controller. Повторить три раза с действующей регистрацией. Это отделит медленный запуск приложения от последствий reboot; данный отдельный случай ещё NOT_RUN.
2. **Windows native Connect:** измерить внутри controller загрузку PowerShell, Get-VpnConnection, rasdial, активацию plugin/broker и получение конфигурации. Проверить возможность убрать запуск PowerShell из обычного Connect прямым системным вызовом. Это кандидат на изменение, не доказанное ускорение; PKCE, проверки владельца и ожидание завершения cleanup сохраняются.
3. **Короткие имена:** снять трассу резолвера для short/FQDN и сопоставить запросы/ответы с задержкой. Не подменять системный DNS hosts-записью или временным ручным правилом ради PASS.
4. **Расширить измерение:** полный P01 в обе стороны; P02 во время cleanup; P03/P04 и отдельный CLI/backend; затем ARM64 и Linux/macOS. Проверка этой ВМ не закрывает всю матрицу.

Цели 30/60 с остаются текущими smoke-бюджетами, не доказательством удобства 9–13 секунд ожидания. Оптимизация и выпуск нового установщика в эту диагностическую задачу не входили.
