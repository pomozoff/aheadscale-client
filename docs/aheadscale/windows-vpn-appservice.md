# Проверка AppService для системного VPN Windows

Это уточнение способа связи в задаче 1 согласованного прототипа. Границы сохраняются: пакетный VPN-плагин, desktop-посредник того же пакета, существующая Go-служба с прежней авторизацией IPC. Перенос движка и дополнительные привилегии не вводятся.

## Наблюдаемое ограничение прямого канала

В версии `0.1.6.1` настоящий VPN-хост запущен как AppContainer в пользовательском сеансе 2. Desktop-посредник имеет ту же Package Family Name и SID пользователя. Pipe в полном приватном пространстве AppContainer открывается, но проверка личности desktop-процесса из плагина возвращает `ERROR_ACCESS_DENIED (5)` на шаге `verify-server-identity`. Профиль остаётся Disconnected. Это ограничение проверенного метода, не доказательство невозможности всех способов IPC Windows.

Удаление проверки личности, общий незащищённый localhost-порт и расширение прав действующего daemon pipe исключены.

## Кандидат с системным посредничеством

AppService предоставляет службе [CallerPackageFamilyName от Windows](https://learn.microsoft.com/en-us/uwp/api/windows.applicationmodel.appservice.appservicetriggerdetails.callerpackagefamilyname). Microsoft показывает [связь desktop и UWP через AppService](https://github.com/microsoft/DesktopBridgeToUWP-Samples/tree/master/Samples/AppServiceBridgeSample). Связь с нашим VPN-хостом подтверждена на `0.1.8.1`: собственный вызов RPC прошёл, другая подписанная идентичность отклонена. Подробности и границы готовности записаны в [отчёте](smoke-results/2026-10-19-windows-vpn-prototype.md).

```mermaid
flowchart LR
    P[VPN-плагин в AppContainer] <--> A[Обработчик AppService в пакете]
    A <-->|Windows AppService| B[Desktop-посредник]
    B <-->|Прежняя авторизация IPC| D[Go-служба Aheadscale]
```

- Desktop-посредник открывает AppService строго заданной Package Family Name.
- Обработчик принимает только CallerPackageFamilyName своего пакета, полученную от Windows, и отклоняет remote system connection. Поля сообщения не служат источником идентичности.
- Для первого доказательства разрешена только операция чтения состояния службы. Посредник использует прежний защищённый pipe и штатный CLI status; ключи и токены не передаются.
- Плагин выполняет запрос после подтверждённой регистрации посредника. Наличие открытого AppService отдельно не считается успешной проверкой RPC.
- До передачи настоящих IP-пакетов проверяются сообщение в обе стороны, отказ неподходящему клиенту и остановленная служба. Никакого фиктивного Connected.

## Что ещё не подтверждено

Передача IP-пакетов, лимиты очередей, задержка и производительность AppService, переключение двух UI, приватный DNS, перезагрузка ОС и собственно видимый рабочий профиль Windows. Для пакетов потребуется ограниченный двунаправленный обмен с MTU 1280; конкретный способ выбирается после доказательства контроля. Производительность заранее не обещается.

Сейчас используются отдельный опытный MSIX, сертификат разработки в TrustedPeople и операторская VM. Обычная служба `.8`, её регистрация и сервер не заменяются этим шагом.
