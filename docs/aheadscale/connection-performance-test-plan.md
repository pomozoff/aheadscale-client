# Время подключения Aheadscale

Общий протокол для [UI](ui-test-plan.md), [CLI](cli-test-plan.md) и сетевых T01–T04 из [smoke-плана](smoke-test-plan.md). Выполнять на точном комплекте ОС / архитектура / backend. Этот документ задаёт методику, а не объявляет все случаи пройденными.

Первый разбор по этой методике: [Windows 11 x64 `.14`, три тёплых подключения](smoke-results/2026-10-25-windows11-x64-connection-latency.md). Он подтверждает только исходящее направление; полного PASS P01 нет.

## Границы текущей проверки

Измеряется подключение VPN **на уже прогретых ОС и готовом клиентском UI**, с действующей регистрацией. Подготовка ОС, вход в сеанс и запуск/отрисовка UI выполняются до замера и не входят в его длительность. Основная серия — P01; P02 проверяет быстрый повтор, P05 — тёплый CLI. Перезагрузка и автозапуск остаются функциональными регрессиями, их длительность в этой задаче не измеряется.

## Что считать готовностью

- `t_action` — нажатие Connect в UI, команда подключения в системном менеджере либо старт `up` в CLI. Зафиксировать, каким способом вызвано действие.
- `t_network` — восстановление обычной сети: адрес/маршрут, системное разрешение внешнего имени и HTTPS с нормальной проверкой сертификата. Записать используемый endpoint и наблюдатель.
- `t_native_request`, `t_engine_up`, `t_native_connected`, `t_ui_connected` — начало системного запроса, запуск движка, Connected в системном менеджере и в приложении. Значения брать из событий и журналов; недоступные точки оставить неизмеренными.
- `t_http_ip`, `t_http_fqdn`, `t_http_short` — первый правильный HTTP 200 от B по каждому адресу, с точным маркером и ожидаемым `remote_ip`. Аналогично для B → A.
- `t_all` — завершение всех шести проверок T01 в данной попытке. Connected, ping, SSH/RDP и запуск движка — самостоятельные свидетельства, не замена этого момента.

Обычное повторное подключение: `t_all − t_action ≤ 30 с`. Восстановление после потери сети: `t_all − t_network ≤ 60 с`. Потеря сети проверяется на уже работающей ОС, без её перезагрузки.

Исторические 41,67/51,62 с после reboot не используются для оценки тёплого Connect: там была другая точка отсчёта. Дополнительные замеры загрузки ОС/UI для текущей задачи не нужны.

SSO с участием человека — отдельный случай: записать действие, открытие единственной новой вкладки, ответ пользователя и готовность сети. Показывать общую длительность и участок после успешного callback раздельно; от успешного callback до `t_all` — не более 30 с. Зарегистрированное повторное подключение не должно требовать SSO.

## Подготовка и серия

1. Записать версии всех компонентов, source/CI/SHA, backend (Linux kernel/userspace/NM, Windows native или стандартный, macOS текущий или Network Extension), NAT/Direct/Relay, память/CPU ВМ и состояние защит. Подтвердить работоспособность HTTP-ответчиков локально и через уже подключённую сеть.
2. Подготовить наблюдатель **до** действия. Он сохраняет времена на диске; послетестовый ручной запуск curl не измеряет момент восстановления. Вспомогательный ответчик или задача не управляют VPN и не вызывают `up`/Login.
3. Для P01 заранее определить прогрев: ОС/сеанс работают, UI готов, регистрация действительна, одна успешная T01 уже выполнена; старый Connect/Disconnect полностью завершён. Проверить отсутствие оставшегося посредника/задачи старой попытки.
4. Выполнить три попытки одной категории на одном комплекте. Сохранять все времена, ошибки и тайм-ауты, минимум/медиану/максимум. Один удачный повтор не стирает первый отказ; p95 из трёх наблюдений не заявлять.
5. До следующей попытки скопировать файлы диагностики текущего поколения: JSON прототипа перезаписываются. Старый `native-profile-stop.json` не становится событием нового Connect. Идентификаторы PID/поколения и время создания привязать к попытке.
6. Проводить замеры монотонным таймером одного наблюдателя. Для корреляции журналов сохранить UTC и погрешность/интервал опроса. Время разных ВМ не вычитать без проверки синхронизации; файловый LastWrite — приближение к записи события, не точное начало операции.
7. Для Windows native отдельно сопоставить UI → запуск controller/активация пакета → PowerShell/RAS → VPN plugin/AppService → broker/канал → Go Up/management → системный Connected → DNS/HTTP. Фиксированные лимиты ожидания не считать фактически потраченным временем.
8. Снять и вернуть диагностические настройки, убрать только свои ответчики, задачи, правила и файлы по квитанциям. Защиты, подписи и проверки личности остаются включены.

Наблюдатель должен быть лёгким: CLI status, WMI, запуск PowerShell и сам curl имеют стоимость. Указать повышение прав наблюдателя, частоту опроса и добавленные процессы; приложение тестировать с его обычными правами. Трёх исходящих запросов достаточно для локализации задержки клиента; такая диагностическая серия не является полным PASS P01/T01 без обратных трёх запросов.

## Вердикт и запись

- Превышение бюджета любой попыткой — FAIL этой попытки. Штатные лимиты 30/60 с сохраняются; тайм-аут не удалять из выборки.
- Если не было действующего ответчика или наблюдатель запущен поздно, время готовности не измерено; соответствующий случай — NOT_RUN/BLOCKED с причиной. Последующий Connected не превращает его в PASS.
- Производительность оценивается только по тёплым подключениям. Функциональные результаты запуска приложения и reboot не подменяют этот замер. Производительность native preview и стандартного backend не объединять.
